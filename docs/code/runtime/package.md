# Purpose

Generated staging receives the candidate's required one-use activation token (`StagingOptions.activationToken`) from the [browser request](../web/package.md). Its deadline signal stops mounting/checks and removes the panel before activation. Once activation has been asked, staging retains the actual server response, since a synchronous commit may have completed (`GEN-08`, `DATA-10`); server authority independently enforces expiry before writes.

Runs a tool's code where it can't reach anything but the host's bridge (`RUN-01`). The host app (127.0.0.1) frames a wrapper on the opposite loopback name (localhost); the wrapper frames, for each page of the tool, a blank `srcdoc` page frame of its own origin, and in it the tool in a `sandbox="allow-scripts"` frame whose document is served with a strict CSP, so its origin is opaque and it can load nothing but blob: images and media. The tool talks to the host only through one fresh MessageChannel port, bound to its frame and its mount's instance. Framework-free: tools are plain HTML, CSS and JS. The server serves the documents ([runtime routes](../server/runtime-routes.md)).

- `src/staging.ts`: `stageCandidate`, staging before activation (`RUN-03`). It pairs each card-front with the card-back at its place, so a card whose back is hidden fails; a failure names the cards missing and the others made. It holds the tool to none of the person's own rules, which are their data (`VER-05`, A64): it passes the same with none, with Fridays ruled out, with Fridays allowed again and with most weekdays ruled out, and keeps them. Rules are compared whole, by their fingerprints. As the owner chose, it doesn't ask that removing a rule bring back the sessions as they were, since a planner may keep its schedule and only use the day again from then on.

# Invariants

- **Bridge method keys match contracts.** The preamble's object is checked against `BridgeMethodName`; its type-only import is erased before the server inlines it. This keeps the runtime methods, generated manifest and static checker aligned without a runtime import in the tool frame.
- **A candidate is activated only after its checks pass** (`RUN-03`). In the panel it sees only synthetic data and can't write: the bridge refuses a write in the staging phase, and the panel's data handlers refuse one too. A failed check, a check that throws (at once or later), a start that fails or a cancelled staging activates nothing, so the previous version stays with the person's data as it was; the server is never asked. Staging cancelled before it starts mounts nothing, and cancelling ends staging even while a check ignores its signal. The server can still refuse a candidate that passed, such as one planned against data that changed since (`MIG-06`), and then nothing changes either. The panel is hidden from sight, assistive technology and input, yet laid out 320 by 640 px, and the candidate's frame fills it from the moment it is inserted (set through the frame's own style, which a host page's CSP can't block), so the candidate runs at the UI standard's narrow width and a check can measure it. The panel is removed whatever happens.
- **Focus stays visible and motion reduced against a tool's style rules** (`RUN-05`). The server puts the host's styles first in every tool's document, standard or custom. They declare two cascade layers before anything of the tool's: the floor, then the standard. The floor's important rules (a 3 px outline on `:focus-visible`; next to no animation, transition or smooth scrolling under `prefers-reduced-motion`) sit in the earlier layer, so they beat a tool's important rules, layered or not. A transition outranks every important rule, so the floor also stops all transitions on whatever has keyboard focus: otherwise a tool could keep the outline transparent for as long as a transition lasts. A focused element's own transitions pause while it has focus. The standard's normal rules sit in the later layer, so a tool's own styles customise it freely. The layers' names end in a random mark the server draws for each document, so a tool's stylesheet can't add rules to them. The browser tests try all of this against a hostile tool in Chrome and Edge, in both modes. The UI standard's look loads only in standard mode (the stylesheet part of `VER-06`).
- **A tool writes only once the person has used its page** (`GEN-06`). `serveBridge` starts a mount as `starting`, makes it `active` when the wrapper reports the person's first interaction, and puts it back to `starting` when the tool is started again, since its start-up code runs again. A tool in the staging panel (`RUN-03`) stays `staging` and never writes. A write before then gets `not-active`, with a message that says nothing was saved; reads work in every phase. The prompt tells the model the rule (`GEN-06`). This guard is what enforces it: the static check no longer guesses at start-up writes (A60).
- **Nothing reaches a tool that the manifest doesn't describe** (`CON-03`). Every call is checked before a handler runs, and every result is checked against its action's result schema before it is sent; one that doesn't fit is a `failed` reply. A handler's own `BridgeError` passes on with its code and message; any other error becomes "The host couldn't do that.", so nothing of the host, such as a file path, leaks to the tool. TypeScript refuses `serveBridge` if an action in the manifest has no handler.
- **The server checks a data call again** (`RUN-04`). A data handler gets the call exactly as the tool made it and the phase it was checked in (`DataCallContext`), and `serverData` sends both, with the workspace, to the server, which runs the same check with the stored version's capabilities before it reads or changes saved data. Only the server's refusals (such as `stale`, `BRG-04`) reach the tool with their own words; an answer that isn't a reply, such as a refused request or a server error, is the host's failure and reaches the tool as "The host couldn't do that."
- **The host clock is the tool's clock** (`RUN-07`). `clock.now` answers from the `HostClock` the host passes, with the date and UTC offset where the person is, so a test sets the next day instead of waiting for it. Only a tool that declares the `clock` capability gets it (`CAP-01`).
- **One tool runs at a time** (`RUN-02`). Opening another tool disposes the running one first: its wrapper frame goes, and with it the tool's frame, channel and timers. A start still in progress is cancelled, and a start that finishes after something newer came is undone at once, so of several quick opens only the last runs. Minimizing disposes the tool the same way and remembers it; restoring starts it again from scratch. A runtime started from a minimized state stays minimized, so a reload keeps a minimized tool minimized.
- **A tool that stops answering is stopped** (`RUN-02`). The host pings the tool's page through the wrapper; the preamble answers each ping. The host runs apart from the tool, on the other loopback name, so a tool spinning in a loop can't hold it up. After a while without an answer, the host removes the tool's frames and reports `unresponsive`, and the runtime shows the tool as stopped, which a reload keeps; the app can start it again. Only pings it sent are judged, so a timer slowed in a background tab never makes a tool look stuck. Time is measured on a clock that only moves forward, so setting the computer's clock can't stop a tool, and a tool the wrapper started again gets a starting tool's time. Everyone listening when the tool stops hears why, the code that opened it as well as the runtime.
- **Each start of a tool has a host of its own,** `t<16 hex digits>.localhost` (`isToolHost`), so Chrome and Edge run it in a process of its own: with one shared host, a new tool would land in a stuck tool's process and never run. The wrapper's policy frames only such hosts, and the server answers the tool's document, and only it, there.
- **On the port, messages have an envelope, but they are only the tool's word.** Between the wrapper and the tool, the host's messages travel as `{ message }`, the watchdog's as `{ ping }` and `{ pong }`, bridge calls as `{ call }` and their replies as `{ reply }`; the preamble wraps and unwraps them. The tool's code shares its page with the preamble, so it can take the port as it arrives, or change `MessagePort`'s methods, and send any envelope itself. Nothing on the port is trusted for more than the tool could do anyway: a pong only shows the page isn't stuck, and every call is checked by whoever serves the bridge (`RUN-04`). The wrapper's events (`restarted`, `stopped`) and the first interaction come from the wrapper, which the tool can't reach.
- **A reply settles only the call that made it, on the page that made it.** A call made before the port exists waits for it, copied as the port would copy it, so a value the port can't carry fails at once, in the tool. Request IDs carry a random mark of the page, and the wrapper forwards a reply only for a call the current page made and is still waiting on, once; a late reply for a page the tool has left (`SBX-07`) goes nowhere.
- **The person's first interaction is seen by the wrapper** (`GEN-06`). The browser activates a frame and every frame around it (`navigator.userActivation`) when the person clicks, taps or types in it, and only then: the tool's own clicks and events activate nothing, and input on the host page doesn't reach frames of another origin. The wrapper reads the activation of the tool's page frame, which is new for each page of the tool: its sticky `hasBeenActive` says the person used this page. A click on a page the tool left, still active in the wrapper for a few seconds, doesn't carry over to the page that replaced it, and the first click on the new page counts at once. The wrapper checks before passing on each message from the tool, so a write the click caused reaches the host after the click does, and every 100 ms; it tells the host once per page. The bridge (#46) lets a tool write data only after this, so code that runs as the tool starts can't write.
- **Two origins and a sandbox.** The host app is on 127.0.0.1, the wrapper on localhost (the same port), and the tool's document is sandboxed with scripts only, so its origin is `null`. The tool's document carries the sandbox in a header too, so it is sandboxed even if something framed it without the attribute.
- **The tool loads nothing.** Its CSP allows its own inline code and blob: images and media; network, fonts, frames from URLs, workers, objects, forms and base changes are refused. The boundary checks prove it in Chrome (`SBX-01` to `SBX-05`): a hostile test tool tries every kind of request, connection, resource, storage and worker, and neither the probe server nor the local server receives anything, not even a connection. In `SBX-01`, a refused request counts only if the tool's policy reported refusing it, so a request that left and failed for another reason, such as the destination's CORS rules, fails the check. One gap is the browser's: a frame navigation to a blocked address still makes Chrome and Edge resolve its name and connect, with no request sent ([#72](https://github.com/suredo/Tessera/issues/72)).
- **Nested frames are as confined as the tool (`SBX-06`, [ADR 0004](../../decisions/adr/0004-nested-frames-in-the-sandbox.md)).** Frames from a URL, `data:` or `blob:`, objects and embeds don't load. A `srcdoc` or `javascript:` frame inside the tool runs, since CSP doesn't govern it, but it inherits the tool's sandbox and CSP and has an opaque origin of its own, no bridge, no network, storage or popups. The tool can't write into a nested blank frame.
- **The tool can't reach the host page or the person** (`SBX-08` to `SBX-13`): no form is sent, the host page and the wrapper stay where they are, no window, dialog or download appears, nothing of the host can be read, messages outside the bridge get no answer and a handle from an earlier mount reaches nothing, and device features are refused even when the person has allowed them for Tessera. The browser refuses the camera and microphone only after touching the devices, which took 1.5-6.5 s in measured runs, so `e2e/boundary-host.spec.ts` waits up to 30 s for that refusal; no answer still fails, since it could mean a prompt is waiting ([#214](https://github.com/suredo/Tessera/issues/214)). Several layers do this: the sandbox refuses forms, popups, dialogs and downloads before the policy's `form-action` sees them; Chrome and Edge refuse a cross-origin frame moving the top page without a click, whatever its sandbox, so `SBX-09` and fullscreen in `SBX-13` also try from a real click inside the tool, where only the sandbox and the frames' missing `allow` refuse them; the wrapper drops anything the tool's own frame sends except its hello, before checking a mount's origin; and the frames carry no `allow` for device features.
- **One port per page of the tool.** The wrapper accepts a mount only from the host app's origin, through its own parent window, with a port. The tool's page says hello from its own frame to its page frame as it loads, and the wrapper answers with one fresh port; it drops messages of any other instance. The host's messages sent before that port exists wait for it, as the tool's do. A frame nested in the tool can't say hello for it.
- **The tool stays on its page (`SBX-07`).** When the tool navigates its own frame to a runtime document, by assigning `location`, a link, a reload or a refresh, the server answers "No Content", so the browser keeps the tool's page, its memory and its port. Any other page it leaves for (a blank one, or one the wrapper's policy blocks) loads without saying hello: the wrapper starts the tool again in a fresh frame with a fresh port, and the host hears `restarted`. After `MAX_RESTARTS` it stops the tool, and the host hears `stopped`. A second hello from the same frame counts as leaving too.
- **The protocol names are defined once** in `src/protocol.ts`; the inlined scripts repeat them, and a test keeps them equal. The server's guard takes the loopback names from here.

# Depends on / used by

The [contracts package](../contracts/package.md), for the bridge's manifest and its check on each call, and through it zod; the browser scripts the server inlines (the wrapper and the preamble) have no runtime imports. The server's runtime routes serve its documents, and the host app (#53) mounts tools with `mountTool` and serves the bridge with `serveBridge`. `serverData` calls the server's [bridge route](../server/bridge.md).

# Pitfalls

- **A check measures the tool only once its frame has its width** (`VER-02`, `VER-03`, L-91). On a cold browser the tool's frame could still be 0 px wide when a check measured it, as Chrome may not lay out a frame until something asks, and may hold back rendering of a frame from another site that lies outside the window. So, as a mitigation, the staging panel lies inside the window, at its top left, transparent and behind the page, inert and hidden from assistive technology, rather than off-screen as it did (L-102); whether the off-screen position caused the one CI failure isn't established, and the acceptance check's passing case stays quarantined (`ENG-20`, [#337](https://github.com/suredo/Tessera/issues/337)) until it is. Otherwise: the smoke check saw a page as wide as its widest control, and a behavior check saw nothing shown. While a check waits for its answer, the wrapper reads its frames' boxes every 50 ms for up to 6 s, which lays them out and gives the tool's frame its width; the preamble's smoke report and behavior steps wait up to 5 s more for the frame to have a width. Neither changes what a check measures or accepts. A frame that still has no width then can't be measured, so the check fails saying so, as Tessera's problem, not the tool's: a behavior step says that rather than that nothing shows a hook, and the smoke report says it rather than reading the width as scrolling sideways (#308).
- **The smoke check's report is the page's word.** The tool's code shares the page with the preamble and can reach its port, so a tool could send a report of its own. The smoke check judges quality, not safety; the sandbox and the [static check](../server/checks.md) do that.

- **A stuck tool's process lasts a few seconds.** Once the watchdog removes its frames, Chrome and Edge end the process of its tool host within about five seconds; until then it keeps one core busy. One lifecycle test reloads the host page right after a stuck tool was stopped; it once timed out in Edge on CI waiting for the page's script ([#83](https://github.com/suredo/Tessera/issues/83), `ENG-20`). The best-supported explanation, not a captured reproduction: the wait polled on animation frames, which a page that isn't painting, as on a busy machine, doesn't get; in 200 local runs the page always loaded. The browser tests now wait for a test page's script on a timer (`e2e/support/ready.ts`), and the test is back from quarantine. If it fails again, its trace will show what happened. The bridge's clock test once found its host page not answering for over 5 s, in Chrome on CI: one run of about 116, with no slow step of its own ([#98](https://github.com/suredo/Tessera/issues/98)). It waits 15 s now, like the bridge's other slow waits, since `RUN-07` is about which clock the tool gets. To tell a stalled page from a slow browser next time, the test host page logs any task that blocks it for a second or more, and a failed test keeps a trace with that log.
- **A tool's frame allows scripts only,** so a `<form>` never submits and its submit event never fires. A tool adds with buttons and keys instead; the sample tools learned this the hard way ([development data](../scripts/dev-data.md)).
- **The watchdog's timings are the host's to set** (`WATCHDOG_DEFAULTS`: a ping a second, stopped after five seconds without an answer, ten while starting). The tests use shorter ones.
- **The bridge doesn't check record revisions.** A stale change is the patch engine's to refuse, on the server (`DATA-02`, `BRG-04`); its data handler passes the refusal on as a `stale` `BridgeError`.
- **The host app keeps the state, not the runtime.** `createRuntime` reports each `RuntimeState` and starts from one it's given; where it is kept (the workspace, from #53) is the app's choice. The tests keep it in `sessionStorage`.
- **The floor isn't proof that focus can be seen.** It sets the outline; it can't make it visible. CSS ranks an element's `style="… !important"` above every important rule in a stylesheet, so a tool can remove one element's outline that way, and a tool's script can remove the host's styles. Its stylesheet can also clip or cover an outline (`clip-path`, an ancestor's `overflow`, an element on top). The static check (`VER-01`, M2) must flag removed outlines and inline importants, and the smoke check (`VER-02`) must look at the rendering itself. The browser tests record the inline case as it is.
- **The browser tests load the runtime as one bundle.** `packages/web/e2e/support/sandbox-host.ts` builds `src/index.ts` with Vite, with the contracts and zod it imports, once per test worker, and its test page exposes `mountTool`, `createRuntime`, `serveBridge`, `serverData`, `stageCandidate`, `stubCheck` and `smokeCheck`. The wrapper and the preamble are still inlined by the server, unbundled. `packages/web/e2e/bridge.spec.ts` serves a hostile tool the real bridge over the real port. With `{ data: true }`, the test host also opens a temporary data folder (`ENG-19`) and serves the real bridge and activation routes from it. A test tool given as plain code runs in custom mode, with the floor but not the standard's look, so the boundary tests' tools keep the styles they set; `packages/web/e2e/styles.spec.ts` gives its tools a mode. `packages/web/e2e/bridge-data.spec.ts` runs `BRG-04` from a tool's click to the saved data, and `packages/web/e2e/staging.spec.ts` stages a candidate and activates it, or doesn't, against saved data (`RUN-03`). `packages/web/e2e/smoke.spec.ts` stages a tool for each way the smoke check fails, and one that passes.
- **The browser tests share one host and one prober:** `packages/web/e2e/support/prober.ts` is the hostile test tool each boundary spec gives its own checks to, with `probe` and `nothingArrived`. `packages/web/e2e/support/sandbox-host.ts` starts the local server and the probe server, records every request and every connection both receive, and mounts tools on a small test page. A check resets it once the tool is ready, so whatever arrives after came from the tool.
- **A restarted tool forgets what it held in memory, and misses what was sent while it left.** A message the host sends after the tool leaves its page but before the host hears `restarted` goes to the page that left and is lost, so the host should send what the tool needs again when it hears `restarted`; the lifecycle (#45's next pull request, `RUN-02`) builds on this. Tests wait for `restarted` and the new page's hello before sending to it: a fixed pause raced the wrapper's one-second hello grace on CI's Windows runner.
- **A slow page may be taken for one that left.** The wrapper waits a second after the frame loads for its hello; a page that takes longer is started again.
- **The inlined scripts can't import at runtime.** Type-only imports are erased before inlining. Change a protocol name in `src/protocol.ts` and in both scripts, or the test fails.
- **The page frame is `srcdoc` because of the server's guard.** The guard tells a tool asking for a runtime document, which it keeps on its page (`SBX-07`), from the wrapper starting one by the request's referrer. A plain blank frame's requests carry none; a `srcdoc` document's carry its parent's address, the wrapper's. The page frame loads before the tool's frame goes in, and it takes the wrapper's policy, so it is sized through style properties, not inline styles.
- **Node prints an experimental warning** the first time the server strips the scripts' types (`stripTypeScriptTypes`), as it does for `node:sqlite`.
