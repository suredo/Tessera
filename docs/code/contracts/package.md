# Purpose

Defines each shape that crosses a boundary once, with zod (`CON-01`): model outputs now, and bridge messages, artifacts and stored records from M1. The host validates with the zod schema, TypeScript takes its types from it, and the JSON Schema handed to the CLI is generated from it, so the three can't drift apart. So far it holds the answer of the intent stage (`GEN-01`), drafted for the M0 live spikes and used by the [intent stage](../server/intent.md), and what crosses the provider boundary: stages, efforts, error kinds, normalized usage (`CLI-04`) and the scripts a scripted provider answers from. The first stored records are an evaluation run's call ledger and request log (`OBS-01`, `OBS-02`), the first artifact is a tool version (`CON-04`, `DATA-04`), and the first change to a tool's data is a patch batch (`DATA-02`). Workspaces, their version history and saved tools are the first records the server keeps for a person (`DATA-08`), the trash says what is deleted and when it goes (`DATA-09`), and an export archive's manifest says what it holds (`DATA-05`). The bridge manifest lists everything a tool may ask of the host (`CON-03`), and the checks on each call are made from it (`RUN-04`).

# Entry points

- `dataReplySchema` (`DataReply`) defines data results once, also used inside mixed replies alongside verified interface facts. A candidate's optional data-pending flag asks the browser to finish only after activation. `FINISH_DATA_ROUTE` accepts `finishDataRequestSchema` (`FinishDataRequest`): workspace, candidate hash and the required opaque request token; smoke repair requires the same identity. Instructions, original expiry and repair counts remain on the server. Equal code hashes cannot identify another request's continuation.
- Generation replies now distinguish committed data-change facts from pending confirmation, which contains only an opaque host token, workspace name and before/after preview. `CONFIRM_DATA_ROUTE` accepts only that token and an explicit approve/cancel choice; patch operations and revisions never travel back from the browser. Dedicated data unchanged/cancelled/stale/clarify/cannot answers keep host outcomes truthful.
- Chat data planning uses `dataPlanSchema` (`DataPlan`): an existing patch batch and summary, unchanged, clarify, or cannot. It reuses `patchBatchSchema`, so a model cannot supply add IDs or replace whole data. `dataChangePreviewSchema` describes host-made before/after records for the upcoming confirmation flow; it is not model output.

It refuses code, unknown operations and anything out of bounds (`MIG-01`, `MIG-02`).

# Invariants

- **Cancellation transport uses opaque host capabilities.** `requestControlSchema` is the registration reply and cancellation request; `cancelRequestReplySchema` reports whether a known live registration was stopped. The initial generate request optionally carries `controlToken`; continuation contracts carry only their existing server-owned tokens, so clients cannot reassign cancellation ownership. Cancellation acknowledges future authority revocation and does not claim rollback. The browser has not adopted this opt-in transport yet ([generation](../server/generation.md), #152).
- **Progress uses the same capability** (`GEN-16`, `CLI-07`). `PROGRESS_REQUEST_ROUTE` takes a `requestControlSchema` token and answers `requestProgressSchema`: the stage (`waiting` or one of `STAGES`, or `null`) and whole seconds since the request was sent. Unknown, finished and cancelled requests all answer `null` and 0, so the reply says nothing about other requests.

- **Public bridge method metadata is shared** (`CON-03`). `BRIDGE_METHODS` defines method names, argument roles, action selection and the existing page-value isolation classification. The runtime object must implement exactly those keys; the generated manifest and prompt projection derive from it, and the server static check validates direct calls against it. This preserves the DOM check's existing exceptions for `call`, `send` and `assetUrl`; it does not claim that every return is JSON (`assetUrl` returns a blob address, and `onMessage` returns an unsubscribe function).
- **Candidate replies identify creation versus editing.** `generateReplySchema` carries `operation` so the host can word the verified activation result appropriately. Its answer kinds also include unchanged and stale; neither is a candidate and neither starts staging. An answer's optional `reason` is the model's own words, for cannot and for unchanged.

- **Edit output is explicit and bounded by existing contracts** (`CON-02`, `GEN-07`). `editSchema` (`Edit`) is edit or cannot; an edit has a plain summary, independent unchanged/style/replace file modes (style carries the complete CSS alone, so the HTML and JavaScript stay as they are, `GEN-14`) and unchanged/migrate data modes. Migration uses the existing migration contract; code and cannot/summary fields reuse creation's definitions. Name, capabilities, pins, UI mode and session entries cannot be supplied by an edit. The committed `edit.schema.json` is generated from the same zod definition.

- **Smoke repair reports are bounded** (`GEN-09`). `SMOKE_REPAIR_ROUTE` takes `smokeRepairRequestSchema` (`SmokeRepairRequest`): a workspace UUID, the stored version hash, one to twenty nonempty findings, each at most 8,000 characters, and which check failed, smoke unless it says behavior (`VER-03`). A candidate reply names the verification profile whose behavior check staging runs, from the server's intent, or null. It answers with `generateReplySchema`; original requests, language and repair counts stay on the server. The HTTP request also has the generation route's 16 KB byte limit.

- **Stored JSON is kept exactly or refused whole.** A JavaScript object can't keep an own `__proto__` key, and zod's own JSON schemas silently drop one, so `jsonValueSchema` and `jsonObjectSchema` refuse any object with that key, at any depth, before parsing; the generated JSON Schema refuses it too (`propertyNames`). Every other key is kept, including `constructor` and `toString`. Codex's review of [pull request 63](https://github.com/suredo/Tessera/pull/63) found the silent loss.
- **One definition.** A shape exists only as a zod schema here. The files in `schemas/` are generated and never edited by hand. A test fails while they differ from the zod definitions.
- **zod and the JSON Schema agree.** Constraints are written so they appear in the JSON Schema too: discriminated unions, enums, patterns, strict objects. A zod-only refinement would let the model's contract and the host's check disagree. The intent tests check both on the same valid and invalid samples.
- **JSON Schema draft-07.** Claude Code checks `--json-schema` with a draft-07 validator and refuses draft 2020-12: the CLI contract spike's first live call found it on 2.1.296 (#19). Every schema that leaves the process comes from `jsonSchemaOf`, and the intent tests validate with the same kind of validator. For today's contracts the two drafts differ only in `$schema`.
- **A field means one thing** (`CON-02`). Each `kind` of intent is its own branch: `savedToolId` exists only for `open_saved`, and `null` means only "nothing".
- **Numbers name their unit** (`CON-05`). A numeric field ends in a unit (`Ms`, `Seconds`, `Minutes`, `Hours`, `Days`, `Bytes`, `Px`, `Percent`, `Tokens`, `Usd`), or it is unitless: a name ending in `Count`, `Index`, `Version` or `Revision`, or exactly `count`, `index`, `version` or `revision`. A test checks every contract, looking through unions, intersections and shared definitions (`$ref`) while keeping the field's name. A new unit is added to `UNIT_SUFFIXES` in `src/units.ts`, which keeps both lists.
- **The bridge is described once** (`CON-03`, `P3`). An action exists only as an entry in `BRIDGE_ACTIONS`; `checkBridgeCall`, the manifest file, and from M2 the prompt's API section and static checks, all read it. Every tool may read and change its own data; an action that needs more names a capability, which the tool must declare in its version (`CAP-01`), so an undeclared action is one whose capability is missing.
- **A call is checked in a fixed order, and changes nothing** (`RUN-04`). A call from another instance is dropped without a reply, since its port isn't this one (`BRG-05`). Then one walk, with bounded work, checks that the call is plain JSON data at most `BRIDGE_MAX_DEPTH` levels deep, so a `Date`, `Map`, `NaN`, an undefined field, a cycle, or a list with holes or named properties is refused rather than changed on the way, and nothing later runs out of stack. A port keeps shared references, which JSON writes out once per use, so the walk counts the written size of every use, never more than JSON writes (commas only between entries), and stops as soon as it passes `BRIDGE_REQUEST_LIMIT_BYTES`, so a call under the limit always passes the walk: a tiny graph that would expand without end is refused after a bounded number of steps, while a small value used twice is fine. Then come an envelope with exactly a request ID, an action and object arguments, a listed action, its capability declared, a write only once the tool is `active` (`GEN-06`), its own size limit, and arguments that fit its schema. Each refusal has a code and a plain message, and every refusal with a reply carries the request ID when the call has a usable one, read right after the instance check. Record revisions are the patch engine's to check (`DATA-02`, `BRG-04`).
- **No argument can point outside the tool's data** (`BRG-07`). No action takes a path, a URL or a workspace, every argument object is strict, and a test checks that no argument's name looks like one.
- **Platform-free.** The browser host, the sandboxed runtime and the server all import this package, so `src/` uses no Node or browser APIs. Only `scripts/` and `test/` use Node.

# Depends on / used by

Depends on zod. The server uses it, its provider adapters included, and so does the evaluation harness; the [runtime](../runtime/package.md) serves the bridge with `checkBridgeCall`, `BridgeArgs` and `BridgeResult`; the host and the live spikes (#19, #20) will too.

# Pitfalls

- **`checkBridgeCall` is only the first half.** The host page and the server both run it (#46): the server has the final say, since it holds activation and revisions. Until the bridge reaches the port and the data, the bridge checks run here, on the function; the hostile tool in the sandbox follows.
- **After changing a contract, run `pnpm contracts:schemas`** and commit the result, or the schema test fails.
- **zod records drop a `__proto__` key silently,** while the JSON Schema refuses it. `refusingReservedKey` keeps the two agreeing (`CON-01`): it refuses the whole value before zod parses it if any object in it has that key, at any depth, so both validators refuse the same input and nothing sets a prototype. The stored JSON schemas (an artifact's data schema and defaults, a workspace's data) and the patch batch all use it; a new contract carrying free-form JSON across a boundary should too, through `jsonValueSchema`, `jsonObjectSchema` or `refusingReservedKey` itself, never `z.json()` or a bare `z.record`.
- **The script format is not in `contracts`,** since it never leaves the process: it has no schema file. Usage reaches `contracts` inside the ledger entry. A canned reply's value is any JSON: its shape is the stage's own contract.
- **The intent contract is a draft.** The intent spike (#20) and the generation pipeline (M2) may change it. Claude Code's acceptance of the generated schema, including `oneOf`, is checked by the CLI spike (#19).
- **zod features that only draft 2020-12 can express** (such as tuples written as `prefixItems`) would be written differently or refused by the CLI. Check a new contract's generated file before relying on it.
- **A union contract can't go to the CLI as it is.** The API takes the schema as a tool's input schema, which must be an object at the top level, so the caller wraps every contract as `{ answer: <contract> }` and unwraps the reply ([CLI contract spike](../evals/cli-contract-spike.md)). The files in `schemas/` stay the contracts themselves.
