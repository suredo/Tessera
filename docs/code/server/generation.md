# Purpose

The core of generation (#146): interface requests create or edit a candidate tool; data requests plan validated record patches. Creation stores a candidate with starting data; editing keeps the active tool and entries until activation. Failed checks are repaired by class. Adds can commit after validation; existing-entry changes wait for explicit review. A request that names the waiting review's token (`GenerateRequest.proposal`) may answer it in words: the route passes the waiting changes' summary to the intent stage only when it still holds them for that workspace, and an approving or declining answer comes back as `proposal_answer` with that token, for the app to confirm through `CONFIRM_DATA_ROUTE`; nothing is consumed or applied by the request itself (L-98). Mixed requests edit first, then plan the separate data instruction against the activated tool.

# Entry points

- `src/generation/data.ts`: `planDataChange` asks for a record patch on the data route (60 seconds by default), with one existing schema/shape repair allowance. `checkedDataPlan` binds revisions to the original host snapshot, simulates the entire batch on a copy, validates the target shape and builds before/after facts with host-generated add IDs. `commitDataPlan` applies the frozen plan with version, live shape and per-record revision checks inside the workspace transaction.
- `src/generation/data-action.ts`: `changeData` handles data-only requests, committing adds or returning a host-owned `DataOffer` for explicit confirmation. `applyDataOffer` commits that frozen plan and composes changed/unchanged/refused facts. Route continuations retain at most 100 offers until the original request deadline; tokens are random and consumed before queuing approve/cancel. Confirmation needs no provider or routes discovery and calls no model. A restart, expiry, replay, changed tool or touched-record conflict cannot apply an old plan.
- `src/generation/edit.ts`: `editTool` runs an edit or a per-class repair with the edit output contract; `editedCandidate` checks it without storing anything. `EditInput` carries the original artifact, workspace data for local validation only, structured intent and repair usage.
- `src/generation/edit-pipeline.ts`: `generateEdit` retains the workspace/version/revision captured before intent, checks it again before and after editing, and stores only a changed candidate. An identical result returns unchanged without staging or a history entry, with the model's summary as its reason, so the person reads why, such as that the tool already does it (`GEN-08`, L-79); a concurrent workspace change returns stale without applying the edit. Actual data migration remains activation's transaction.

- `src/generation/create.ts`:
  - `createTool` asks the create stage on its route (`CLI-09`), within `GENERATION_TIME_LIMIT_MS` (`GEN-11`), repairs a failure of the host's checks on the repair route, within `REPAIR_TIME_LIMIT_MS` and `REPAIR_BUDGETS`, and gives a `CreateResult`: a `Candidate`, a "cannot" with its reason, or a failure with its class and findings, each with how many repairs it took.
  - `candidateFrom` is the host's checks on a created tool.
  - `startingDataOf` builds a new workspace's data from the defaults and the request's entries.
- `src/generation/pipeline.ts`: `generate` carries out a request as far as the server goes.
- `src/generation/discuss.ts`: `answerDiscussion` answers a question or an idea (`GEN-19`, A59) with one call on the discuss route (Haiku 5.5 low, `CLI-09`), within the intent stage's time limit. The pipeline replies with a discussion, the answer in words, and builds, changes and stores nothing; a provider failure is a provider failure, as at any stage. The generate route names the answer with a token and keeps it for `DISCUSSION_KEPT_MS` (30 minutes), bound to the workspace it was asked in, or to none open; it grants nothing. A later request that names the token from the same place, while no review waits, is carried out with the answer as context: the intent stage, and then creation or the edit, are told it, quoted, when it fits the room every stage keeps ([prompt assembly](prompts.md)). So is the entry stage, for an entry change and for a mixed request's entry part, planned once its version is active, so "add it" has the figures (A61). A repair of a tool isn't told it, and the acceptance experiment isn't run for such a request, since it sees only the request's words.
- `src/generation/routes.ts`: `generationRoutes` answers the host app's requests on the generate route, each run as a job (`CLI-06`); `GenerationOptions` gives it the store, the job queue, the provider and the routes, and can set the request's and each stage's time limits (`GEN-11`).
- `src/generation/control.ts`: `RequestControls` owns optional registered cancellation capabilities, their jobs and continuation authority, and each request's progress (`GEN-16`, `CLI-07`): waiting while its job is queued, then the stage of each model call as it starts, through a provider wrapper that notes each call's stage, with the seconds since it was sent; no stage between its parts, after it ends or once cancelled. Every request and its model calls are recorded in the [call ledger](ledger.md) (`OBS-01`, `GEN-10`). The progress route answers it for the registration token. Stage names and elapsed time only (ADR 0010).
- `src/generation/result.ts`: `GenerationResult` separates internal candidates from public replies: stages cannot mint activation authority. The route adds a one-use token and original expiry to initial and repaired candidates.
- `src/generation/deadline.ts`: `REQUEST_TIME_LIMIT_MS` defaults to seven minutes. `withinRequestDeadline` shares an absolute expiry across server stages, aborts calls at expiry, caps each call by the smaller of its stage limit and remaining time, and checks again before an answer or candidate can be stored.
- `src/generation/smoke.ts`: `repairSmoke` loads the failed stored version and repairs it using the original interface request, intent language, diagnostics and remaining class budgets, for a smoke failure or a profile's behavior failure (`VER-03`), each with its own budget of one. A candidate carries the profile its intent named, so the browser runs that profile's check. The route keeps the continuation for a repaired candidate too, with the repairs spent so far and the original deadline, while it fits a profile and the other check's repair is unspent, so a smoke repair and a behavior repair can follow one another, while a second of either is refused without a call. It keeps it only then, as a continuation kept for nothing would make the same candidate look busy to the next request until the deadline; and the [browser](../web/package.md) lets its request go through the cancel route once no repair is left, which frees what was kept. `SmokeRepairContext` is the server-owned continuation remembered by the route.
- `src/generation/time-limits.ts`: `StageTimeLimits`, each stage's own time limit (`GEN-11`), `DEFAULT_STAGE_TIME_LIMITS` and `checkStageTimeLimits`, which merges configured limits over the defaults and refuses bad ones.
- `src/generation/acceptance.ts`: the acceptance stage (`VER-09`, A49), off unless `GenerationOptions.acceptanceChecks` is set, which the launcher does by default since M3's experiment (A57). `writeAcceptance` asks it once on the acceptance route, the cheapest (`CLI-09`), within the intent stage's time limit, with the request and its language only, and gives an `AcceptanceResult`: checks, none with a reason, or a failure it can't use. A sign-in, usage, model, effort or cancel failure ends the request as at any stage; any other leaves the tool to be made without checks.
- `src/generation/two-pass.ts`: two passes for big tools (`GEN-17`, A17), off unless `GenerationOptions.twoPass` is given. `twoPassPlan` decides from the intent's features with `TwoPassOptions` (`TWO_PASS_STARTING_POINT`: at least 4 features, a core of the first 2), never from a model's flag (L-37), and gives a `TwoPassPlan` (`Feature`s for now and for later); `checkTwoPassOptions` refuses options with no core or nothing left for later.
- The answer's contract is the contracts' creation schema, with the failure classes beside it ([contracts](../contracts/package.md)). The stage's prompt adds the create part to the [prompt assembly](prompts.md).

# Invariants

- **Data planning sees entries, not interface instructions or code.** Its separate prompt quotes only the declared data shape, snapshot and record revisions, plus the data request/language. Actual context is capped at 12,000 characters before calling a model; at most 100 operations and 64 KiB of preview are accepted. Provider errors stop; schema/shape errors get at most one repair against the same original snapshot. No stage or repair budget is increased. The approved [live chat-data check](../../../evals/reports/2026-10-29-chat-data-check.md) passed an add and a mixed style/replacement case in two calls, with scripted intent/style and actual host approval. Its deterministic replay checks planning, activation and storage preservation; no repair ran live.
- **The host owns data-plan safety facts.** Guessed model revisions are replaced by the planning snapshot's counts, then live counts are checked on commit. Adds use frozen host IDs. Unrelated live record changes survive; a changed target or tool version refuses the whole batch. The resulting live data must fit the original active tool's schema. Identical data does not create history. Any batch containing a replace/remove waits for the person's explicit before/after confirmation; until then its entire batch stays unapplied. Confirmation rechecks expiry/cancellation immediately before the synchronous transaction and cannot accept a client-supplied patch.
- **What a tool leaves out is said** (`GEN-08`). When a request is possible only in part, because the rest needs what no tool here can do (the internet, outside pictures or videos), the create stage makes the part it can and names each part it leaves out in `leftOut`, which the candidate reply carries to the [browser](../web/package.md). An edit whose doable part the tool already has keeps the list too: the unchanged answer and a mixed request's unchanged interface carry it, and nothing is stored (`GEN-07`). A smoke repair's answer replaces the failed one's. Each part gets the same plain-words check as the summary (`leftOutProblems`, `GEN-12`). The create part says this; the edit part has no room in its prompt budget, so edits rely on the field's description in the answer's schema. A core pass never lists its later features there. Nor does any answer list a part another tool here could do, or one the person says comes later: both the create part and the field's description say so (L-90), since the host shows the list as what no tool can do.
- **Generated words are plain** (`GEN-12`). A creation's name and summary, and an edit's summary, that use a word for Tessera's own parts the request didn't (`internalTerms`) are a schema-shape failure, repaired with the words named (`plainWordProblems`), so a name like "Capability declaration fix" never becomes a tool (L-36). A refusal's reason ("cannot"), from creation, an edit, any repair (smoke included) or a chat data plan, is final, so it isn't repaired: one that uses such a word reaches the person as the host's plain `PLAIN_CANNOT_REASON` (`plainRefusal`), and the model's own words go with the reply as a finding, so the ledger and the details view keep them (`GEN-10`).
- **Edits declare file and data changes separately** (`CON-02`, `GEN-07`). Files can stay unchanged, change only their style (the complete CSS, with the HTML and JavaScript kept by construction, `GEN-14`), or be replaced in full. A look-only edit that answers with replaced files must still keep the HTML and JavaScript identical, so older recorded answers replay; every repair of it, smoke, static or shape, is quoted its failed answer as style only. Data can stay unchanged or migrate one version with the existing declarative migration contract. Thus unchanged files can still produce a real data-declaration change. The host returns `unchanged` only when the complete canonical artifact is identical; a model summary never decides whether a version changed.
- **Edits keep what wasn't asked to change, checked by the host** (`GEN-13`). The edit contract can't name or replace the tool's name, capabilities, pins, UI declaration or starting entries, so the host keeps them; a test edits, activates and finds the same name and declarations. Data changes only by a declared migration that loses no value (`migrateData` with losses tracked). A look-only edit keeps the HTML and JavaScript identical, sent and answered as style alone (`GEN-14`). **M2 limit:** whether an edit that changes behavior also keeps the look and unrelated behavior is asked of the model, not checked: that needs M3's behavior checks (`VER-03`).
- **Edit migrations cannot lose existing values.** A data change needs an edit that isn't look-only, exactly the next version and a changed schema; it no longer needs the intent's `behaviorChange`, since refusing it sent the repair to drop the data change and keep the code relying on it (L-97). The target schema/defaults pass the same bounded data checks as creation (`dataProblems`); both current entries and old reusable defaults migrate on copies with loss tracking. Any removed or replaced value, invalid record naming/id, incompatible result, or defaults differing from the migrated old defaults is refused. No workspace data is sent to the prompt or written here. Destructive edits and other declaration changes answer cannot or fail; confirmation flows are outside this slice.
- **Edit repair retains the original baseline.** Each call uses the original code and declarations, with a failed edit quoted separately when its shape is valid. Edits and their schema/static/smoke repairs use the same edit contract and host checks, existing per-class counts and the edit and repair limits (180 seconds each by default); provider failures never repair. Browser smoke-repair continuation is integrated separately.

- **The answer is a discriminated union** (`CON-02`): a tool, or "cannot" with a reason. No null means two things, and capabilities are limited to the bridge's own.
- **Defaults and the request's entries stay apart** (`GEN-05`). The artifact keeps only the reusable defaults. A new workspace starts from the defaults, with each list the request gave entries for extended by them. The request's entries never become defaults.
- **Nothing is stored or run before the host's checks.** In order:
  - the declared data shape must be one Tessera can check (`DATA-03`);
  - the defaults and the starting data must fit it, within the most data a tool may hold (`DATA-06`), and every record must be one the patch engine can change (`DATA-02`): its list's name, its id and its field names must be ones the patch contract accepts (one definition, the contract's own), and its id unique in its list. As the patch engine counts a list as records only when every item is one, a list holding any object must hold only records, and an empty list is held to the name rule unless the schema declares it a list of other values (an item type that rules out objects, written as one name or a list of them);
  - the artifact must match its contract (`CON-04`);
  - the static check must pass with the artifact's actual capabilities (bounded `VER-01` coverage, [static check](checks.md)): sandbox rules, known direct bridge methods/actions, declared action capabilities and host-clock rules; a write as the tool starts is the bridge's to refuse when it runs (A60). These findings use the existing static repair budget; edits check the retained capabilities too. Starting entries belong in host-installed output, with tool writes deferred to user actions.
- **Every failure is classed** (`GEN-09`):
  - schema-shape: a data shape, data or answer that doesn't fit, which repair can fix;
  - static: findings with the part and line;
  - provider: any other failure of the call (sign-in, limits, time), which is never repaired.

  Smoke failures come from browser staging. Behavior failures wait for M3: the class exists in the contract, but until M3's behavior checks nothing produces it, so nothing repairs it (`GEN-09`'s M2 limit).
- **A failure of the host's checks is repaired by its class** (`GEN-09`). Schema-shape and static failures go to the repair stage, on its own route (Sonnet medium, `CLI-09`), with their class's prompt part, what the checks found and the failed answer quoted, or, for an answer of the wrong shape, the request alone. The repair answers as creation does, and its answer goes through the same checks. Each class has its own budget in one request, one repair each for now, so a static failure after a shape repair still gets its own, and the result says how many repairs it took (A40). A provider failure, in creation or in a repair, is never repaired. A repair may also answer "cannot".
- **A look CSS alone can't make is tried as a code edit** (`GEN-14`, `GEN-08`, L-96). A look-only edit sees only the tool's page and style, and says it can't when CSS alone can't do what was asked, such as motion that follows the mouse, rather than imitating it. `generateEdit` then asks once more with the tool's whole code, as an edit that isn't look-only; if that can't either, the person is told so. Both calls share the request's repair budget, so a repair class the first spent isn't spent again. The intent stage doesn't count motion that follows the mouse, dragging or scrolling as look-only.
- **An edit keeps the tool's own profile** (`VER-03`, L-94). Only a new tool takes its profile from the intent. An edit takes the one its tool's current version was checked by (`noteOf`), or none, whatever its intent named, so the edit, its repairs and staging check the tool as the kind of tool it is, and an edit never imposes a new profile's hooks and check the person didn't ask for.
- **Checks from the request** (`VER-09`, A49, A57). With `acceptanceChecks` set, as Tessera starts by default, a new tool that fits no profile and is made in one pass gets checks from the acceptance stage before it is made. Creation, and each repair of it, is told their hooks and what each checks, as a profile's rules are (`VER-04`); the candidate carries them (`acceptance`) to staging, and a smoke or behavior repair keeps them from the candidate it repairs. A tool that fits a profile, an edit, or a two-pass core gets none. With them off, nothing changes.
- **A big new tool can be made in two passes** (`GEN-17`, in part). With `twoPass` set, a create or new-tool request with enough features gets the `core` prompt part: the core pass builds a complete tool with only the first features, and its smoke repair keeps to them. The candidate's `followUps` names the features still to come, in order. Once a version is active, the app asks `FOLLOW_UP_ROUTE` with its activation token, workspace and hash. The server keeps the rest under that token, consumed once before any call, for the request's deadline plus one request's limit, and keeps the request's registered control as long, so Cancel still stops what is to come; the previous candidate's activation authority isn't extended. It refuses a token it doesn't hold, another hash, or a version that isn't the active one (answered as stale). Each feature is its own request with a request's whole time limit (`GEN-11`), run as an edit (`generateEdit`) with the host's own intent: an edit of the tool open now, in the request's language, allowed to change behavior, with that feature alone, so no intent call is spent on it. The next feature's continuation follows the new candidate, its smoke repair included. Whether two passes beats one, and so the default, is measured live before it changes; until then the option stays off.
- **The prompt's schema keywords are the host's own list,** the one the data shape is checked against, so the model is told exactly what passes.

- **Mixed instructions stay apart** (`GEN-04`). Only the interface instruction reaches editing and its repairs. A server-owned continuation retains the data instruction, language, original expiry and shared per-class repair counts. Smoke and finish-data requests require the candidate's opaque token; maps key continuations by that identity, with workspace/hash checked before consumption. Activation consumes its own authority while leaving the independent data continuation eligible until the same original expiry. An expired old POST cannot consume a later same-workspace/hash request's instructions or budget. After staging/activation, finish-data consumes its continuation and checks the active version before planning against its new shape. Identical interfaces still run the separate data part; failed interfaces never do. Smoke repair revokes the old continuations and transfers remaining data work to the repaired candidate's fresh token, without another smoke allowance. Outstanding equal workspace/hash candidates are refused before replacing instructions. Continuations are bounded to 100 and disappear on restart/expiry. Missing, premature and replayed follow-ups spend no model call or write.
- **The pipeline carries a request as far as the server goes, and activates nothing.** The intent stage decides, with the open tool and its lists, and the saved tools, the most recently used first, from which it is shown a catalogue (`GEN-18`).
  - Clarify, unsupported and ask-to-split are answered as they are, and a listed saved tool is offered to open.
  - An interface edit runs `generateEdit` against the open tool. Data requests run `changeData`; mixed requests edit first and retain their data part for the activated version. An unchanged edit plans data immediately and returns both facts.
  - Create and new tool run the create stage on the interface part. A checked candidate is stored, and its workspace starts with its starting data: the open workspace if it has no tool and no data yet, or a new one, named after the tool and described by the creation's summary (`APP-04`).
  - The reply gives the candidate's mount (`v-` and its hash) and its defaults as synthetic data, for staging (`RUN-03`). The host app stages it behind the smoke check and activates it (`DATA-10`), and activation keeps the starting data.
- **A creation failure stores nothing.** A candidate that still fails the server's checks after its repairs is answered with a plain sentence and its findings. A provider failure, in either stage, gives the adapter's plain message. A setup problem, or a routes file Tessera can't use, is answered in plain words before any call. A smoke failure happens after the initial candidate and starting workspace have been stored; its repair activates nothing and changes no workspace data.
- **Smoke repair continues the same request** (`GEN-09`). The browser sends the workspace, candidate hash and smoke reason to `/api/generate/repair-smoke`, which answers with the generation reply contract. The route retains at most 100 continuations until the original request deadline, with its request, intent and repair counts. It consumes a continuation before calling repair, so duplicate or concurrent reports cannot buy another repair; a restart or expiry loses eligibility. The repaired candidate gets no new continuation. Schema and static failures from the repair use only their remaining budgets; provider failures are never repaired.
- **Smoke repair never reinstalls starting data** (`GEN-05`). A creation's failed answer comes from the stored artifact, with empty initial state, and its workspace must still have no active version. An edit's continuation keeps the original active version and the expected data revision, reconstructs the failed edit against that original artifact, and uses the edit stage/contract. Both repair paths must preserve the failed candidate's exact data declaration and defaults and retain the expected workspace revision before and after the call. The browser stages the repaired version against its defaults and activates it against that same revision. Existing entries are kept exactly once; an edit's requested migration is applied only at activation.
- **One request at a time** (`CLI-06`): each runs as a job in the server's job queue.
- **Registered cancellation is opt-in server transport** (partial [#152](https://github.com/suredo/Tessera/issues/152)). `POST /api/generate/register` mints a bearer token; an initial request's optional `controlToken` claims it once before asynchronous provider discovery. Cancel posts that token to `/api/generate/cancel`, marks its control stopped, cancels its queued/running jobs and revokes its candidate, smoke, mixed-data and review tokens. Unknown tokens return `cancelled: false` and never register future work. A cancellation before submission prevents later setup completion from starting a job. Continuations inherit their original control through server-owned token identity; the caller cannot switch owners. Completed synchronous data or activation commits stand. Cancellation acknowledges revoked future authority, not rollback or proof that nothing changed; callers must retain confirmed facts and report a lost commit response as uncertain.
- **Cancellation ownership is bounded and expires closed.** At most 100 registrations are retained; capacity refuses new registrations without evicting active owners. Unused registrations expire after seven minutes. Once claimed, setup must finish within that registration expiry; queue waiting then precedes the normal request deadline, which starts when the initial job runs. Continuations keep that deadline. Expired registrations and their owned tokens are swept on the next registration; cancelled controls remain until expiry so later setup and continuation requests still fail closed. Queue outcomes record jobs actually cancelled; registration state is in memory and restart loses its authority. Existing clients without `controlToken` keep their previous behavior. The [browser](../web/package.md) now registers and cancels requests, preserving committed facts and uncertain responses. Actual server stage names and elapsed time remain follow-up work in #152.
- **Every stage has its own configurable limit** (`GEN-11`). `GenerationOptions.stageTimeLimitsMs`, and `LaunchOptions.stageTimeLimitsMs` through the [launcher](launcher.md), sets any of intent, create, edit, repair and data; the rest keep `DEFAULT_STAGE_TIME_LIMITS` (60, 180, 180, 180 and 60 seconds). `checkStageTimeLimits` refuses an unknown stage, or a value that isn't a whole number of milliseconds from 1 to 2,147,483,647, when the routes are built, so a bad setting stops startup. A tool's repair, created or edited, gets the repair limit; a data plan's repair keeps the data limit. Direct callers of the stage functions get the defaults. Each call is still capped by the time left in its request. The defaults were kept after M2's measurements ([ADR 0012](../../decisions/adr/0012-time-limits-after-m2.md)).
- **Server stages share a request deadline** (`GEN-11`). The [browser](../web/package.md)'s staging is held to the same deadline. The clock starts when the queued generation job starts, after provider discovery. `GenerationOptions.requestTimeLimitMs` configures its positive timer-sized budget (seven minutes by default). Intent, creation/edit and their repairs share it. Time between candidate generation and smoke repair counts too; queuing a repair cannot reset expiry. Calls receive the remaining budget and a combined cancellation signal. Expiry is a plain provider failure, never repaired. Late answers are discarded, and synchronous validation is followed by a clock/signal check immediately before storing a version or new workspace. The queue waits for an aborted provider to settle before starting the next job; no timed-out result becomes a candidate.
- **Candidate authority expires with the request** (`GEN-11`, `DATA-10`). The route keeps at most 100 opaque activation tokens, each bound to workspace, hash, planned revision and original deadline. Matching consumes the token before activation; a refusal also consumes it. Wrong fields cannot consume another candidate's authority. Expired, evicted, replayed or restart-lost tokens fail closed, including when later requests produce equal hashes. Consuming a smoke continuation revokes its old candidate token before repair; a repaired candidate retains the original deadline. The guarded activation route checks expiry before validation and again after migration immediately before the first synchronous write. A completed commit retains its success even if time crosses during writes. History restore/undo use their separate host API. The authority each token grants also carries the version's note (`APP-05`): the candidate's summary and the checks it passed. That's the host's code check, run before the candidate was stored, and the start check only when the activation says the app's staging ran it and it passed (`startChecked`): the app's report, recorded as such. An activation without it records the code check alone. The token also keeps the profile the server's own intent named for the candidate, and the behavior check is recorded, with that profile, only when the activation reports the start check and the behavior check passed (`behaviorChecked`) and the server named a profile: the browser can't name one (`VER-08`). Likewise the checks written from the request are recorded, as acceptance, only when the activation reports the start check and them passed (`acceptanceChecked`) and the server gave this candidate checks (`VER-09`).
- **The browser uses the same deadline.** Candidate metadata lets `carryOut` cancel staging at the original expiry, without another smoke repair. Activation keeps its actual response if commit began; a lost response is reported as uncertain and reloads the workspace. Mixed data follow-ups and confirmations retain the original server deadline and verified interface facts. Setup discovery and queue waiting precede the deadline; the browser Cancel uses the same request owner, while actual server progress remains under #152. Direct `generate`/`repairSmoke` callers retain stage limits and their supplied signal without receiving activation authority.
- **A completed synchronous store keeps its result** (`GEN-08`). The pre-store check accepts the storage boundary only while the request is live. Once that synchronous work finishes successfully, a clock crossing during its commit cannot turn it into a timeout with hidden saved work. A store that throws still fails; non-storing outcomes still get a final deadline check. Provider calls remain bounded even after that boundary.

# Depends on / used by

The [provider adapters](providers.md)' routing, the [prompt assembly](prompts.md), the [data shape](data-shape.md) checks, the [static check](checks.md), and the contracts. The pipeline runs the [intent stage](intent.md), then generation, browser staging/activation and the separate data part of a mixed request.

# Pitfalls

- **The first create prompt always assembles in standard mode.** A request for its own design can still answer custom, but its prompt carried the standard's look; a custom-mode first prompt waits for the intent stage to say so. Repair uses the failed answer's mode when it has one.
- **"cannot" overlaps the intent stage's unsupported.** The intent stage should catch those first; the create stage's answer is the second wall, not the main one.
