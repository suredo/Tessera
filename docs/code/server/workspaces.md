# Purpose

Keeps what a person makes always saved (`DATA-08`): each workspace, the history of its tool versions, its data, and the named entries of the saved-tools library. Every change is one transaction in the data folder's database ([storage](storage.md)), committed before the function returns, so there is no "unsaved work" for a restart to lose. The shapes are the `workspace`, `workspaceVersion` and `savedTool` contracts in `@tessera/contracts` ([contracts package](../contracts/package.md)); the tables come from the migration `0002-workspaces.sql`.

# Entry points

- `src/workspaces/workspaces.ts`, each function taking a `Store` (the open data folder's database and clock):
  - `createWorkspace`, `renameWorkspace`, `getWorkspace` and `listWorkspaces` (the most recently changed first). A created tool's workspace can start with its starting data (`GEN-05`), as its first data, with nothing to undo; `replaceData` writes a workspace's data whole, inside the caller's transaction.
  - `recordUse` records that a workspace was opened, and `lastUsed` gives, for each one not in the trash, when it was last used: opened or changed, whichever is later (`APP-03`). Opening changes nothing else, so a workspace's own time stays when its content last changed.
  - `addWorkspaceVersion` makes a stored [tool version](versions.md) the workspace's current one, as the next entry of its history; `workspaceVersions` lists the history.
  - `saveWorkspaceData` replaces the workspace's data and raises its revision.
- `src/workspaces/restore.ts`: `planRestore` says what restoring a version would do without doing it (`RestorePlan`: it keeps the data, or it loses exactly these values, with a confirmation), and `restoreVersion` does it; `listRecoverySnapshots` and `restoreRecoverySnapshot` bring back the unit a lossy restore replaced (`DATA-10`).
- `src/workspaces/undo.ts`: data undo (`DATA-04`). `listUndo` lists the changes a workspace can undo (`UndoEntry`), newest first, and `undoDataChange` undoes one, or returns why not (`UndoResult`). `UNDO_LIMIT` is how many it keeps. `src/workspaces/undo-entries.ts` works out, without touching storage, what a change touched and what undoing it gives.
- `src/workspaces/reuse.ts`: opening a saved tool (`DATA-07`). `continueSavedTool` gives the entry and its linked workspace with its current data (`ContinueTarget`); `useAgain` makes a new workspace from the tool's current version and its reusable defaults, or returns why not (`UseAgainResult`).
- `src/workspaces/routes.ts`: `activationRoutes`, the route at `POST /api/activate` (the activation route of the [contracts](../contracts/package.md)) through which the host page activates a candidate that passed its checks (`RUN-03`). It answers with `activateVersion`'s result, which is the contract's activation reply; a malformed request gets a plain 400, a missing or trashed workspace a plain 404, and a server error a plain 500, none of them changing anything. The [launcher](launcher.md) mounts it.
- `src/workspaces/activation.ts`: `activateVersion` makes a stored tool version the workspace's current one, with its data brought to the version's shape, in one transaction (`DATA-10`), or returns why not (`ActivationResult`).
  - `readWorkspaceData` gives the data as the bridge does (`WorkspaceData`): the data, and each record's revision count by collection and ID. Data the tool hasn't filled yet reads as empty.
  - `patchWorkspaceData` applies a batch of changes through the [patch engine](patches.md), against the records' saved revisions, and returns `{ ok: true, addedIds, workspace }` or the engine's refusal (`WorkspacePatchResult`).
  - `saveTool` (Save to my tools), `renameSavedTool`, `getSavedTool` and `listSavedTools` (by name).

# Invariants

- **Chat can add transaction-local guards.** `WorkspacePatchOptions` extends the existing engine options with an expected active version, a final-data validator and no-op skipping. Those checks run against the live working copy before any data, revision or undo row is saved. `WorkspacePatchResult.changed` distinguishes a committed change from a skipped no-op. Existing bridge callers retain their earlier behavior; schema validation is installed by the chat helper, not silently claimed for every bridge patch.
- **Saved as it happens.** Each function commits its change before it returns; a test changes everything, restarts, and finds it all, both through `openDataFolder` and through a full launch and stop.
- **Rows are checked by their contracts when read** (`CON-01`): each row is turned into its contract's shape and parsed, so a stored record that breaks its contract is never handed on.
- **The history only grows** (`DATA-04`). A workspace's current version is the last entry of its history; going back to an older version adds a new entry, so the newer one stays restorable. A trigger refuses any change to an entry, and an entry must name a stored version (a foreign key).
- **Data is kept exactly, or refused whole.** Data the contract can't keep exactly, such as an object with a `__proto__` key, is refused before anything is saved, so a save that succeeds always reads back the same ([contracts package](../contracts/package.md)).
- **A stale data write is refused.** `saveWorkspaceData` takes the revision the new data was made from; if the data changed since, it saves nothing and says so plainly, so a slower writer never replaces newer work.
- **Each record's revision is saved with the data** (`DATA-02`). `record_revisions` holds every record's count; a record with no row is at revision 1. `patchWorkspaceData` reads the data and its revisions, applies the batch and saves the data, the workspace's revision and the records' revisions in one transaction, or nothing. So a batch planned against an older revision is refused whole even after a restart, with the engine's plain message, while a batch touching other records still applies (`BRG-04`).
- **Replacing the data whole moves every record on.** `saveWorkspaceData` gives each record it keeps its next revision, so a change planned before the replacement is refused rather than applied to different content.
- **A revision is never reused.** A record's row is never deleted while its workspace lasts: a removed record keeps its last count, so a record that comes back with the same ID, as a restore can bring it, continues from there, and a change planned before it left stays stale. The rows go only with the workspace, removed for good from the trash.
- **Every collection and record is its own entry.** The revisions `readWorkspaceData` gives are built from entries, so a collection named `constructor` or `toString` is its own, and reading data never touches what objects inherit. A record ID is never `__proto__` (the patch contract refuses it, as JSON refuses that key), since revisions are kept by ID; a list holding such an item is not a list of records.
- **Activation changes code, shape and data together, or nothing** (`DATA-10`). `activateVersion` checks everything before it writes: that the data revision it was planned against is still the workspace's (`MIG-06`), that the version exists and can be read, that the version's reusable defaults fit its own schema and the data limit (`DATA-03`, `DATA-06`), on every activation, since a version is one unit with its defaults and Use again starts from them, and that the data reaches the version's shape. A new workspace's first version fills its data from those defaults; a later version migrates the data on a copy through the [data shape](data-shape.md) module, checked against both schemas. Then the data and the version's history entry are written in one transaction, so a refused check, a stale revision or a crash during the commit leaves the committed unit as it was; a test throws after the writes to show the rollback. A version whose data shape is older than the data's is refused here: restoring one converts the data with a loss preview (#50, a later part).
- **A restore keeps the data when it can, and loses nothing silently** (`DATA-10`, `DATA-04`). Restoring a version adds it to the history as the newest entry. Data that fits the version as it is stays exactly as it is, with no migration. Otherwise it is converted through the [data shape](data-shape.md) module: migrated forward to a newer shape, or projected onto an older one, keeping what that schema allows. Every value a conversion removes or replaces (a removed field, a value a table replaced, a field an older schema closes off) is listed in the plan, with the record's ID in its path and, for the person, the same place as steps: each field by its name, and each list item by its name (its first title, name, label or text that holds text) or none, with the list it is in (`GEN-12`). An item is found the way its path names it, by its ID when it has one and by its position otherwise, never mixing the two. The steps are added after the confirmation is made, so the confirmation covers exactly the losses, and the preview with them stays within the same bound as before, or the restore is refused as too large; a forward migration that loses nothing needs no confirmation. A restore that loses anything runs only with the plan's confirmation, which names the version, the data revision and those exact losses, so a confirmation never runs a different restore; before it runs, the whole current unit (its version and data) is kept as a recovery snapshot, and that unit must fit its own version, so the snapshot can bring it back, or the restore is refused. If a conversion can't make the data fit, the restore is refused with the reason. Cancelling is never confirming: planning writes nothing. A stale revision, a failed migration or an interrupted commit keeps the committed unit, snapshot included.
- **A recovery snapshot brings back the unit before a conversion.** `restoreRecoverySnapshot` makes the snapshot's version current again with its data, if the data revision is still the planned one, and first keeps the unit it replaces as a snapshot of its own, so bringing one back never loses newer work either. Like a lossy restore, it first checks that the unit it replaces fits its own version, so that snapshot can be brought back in turn, and is refused otherwise. Snapshots go with their workspace.
- **A new workspace has no tool and no data**: its current version and data are null until a version is activated and fills the data from the tool's defaults (`DATA-03`).
- **Every data change can be undone, but never over newer work** (`DATA-04`). `patchWorkspaceData` keeps, in the same transaction, each record it touched: what it was before, where it stood, and its revision after. `saveWorkspaceData` keeps the whole data before. Activation and restore keep none, since they change the tool, and a restore keeps a recovery snapshot instead. `undoDataChange` reverses only that change. Each record it touched must still be at the revision the change left it, and a record it removed must still be gone at the revision it had then (the saved rows keep a removed record's last count), so one that came back, changed and went again isn't overwritten; for data replaced whole, nothing may have changed since. Otherwise it is refused and nothing changes. A removed record comes back where it stood, and an added one goes. Only the records it brings back move to their next revision, so a change planned against any other record still applies. The result must fit the tool's current data shape and the data limit, so an undo from before a shape change can't bring old records back. An undone entry is used up, and its number is never given to another (SQLite's `AUTOINCREMENT`), so asking again for a change already undone never undoes a newer one. The newest 100 entries per workspace are kept, and they go with their workspace. Undo entries keep the assets they name ([asset store](assets.md)).
- **A saved tool follows its workspace** (A32): it names the workspace that Continue opens, not a version, so later improvements are kept.
- **Continue and Use again never move the entry's link** (`DATA-07`). Continue returns the linked workspace, with its title so the target is clear, and its current data. Use again makes a separate workspace, named after the entry unless given a title, with the linked workspace's current version and that version's reusable defaults as its data: never the person's entries, which stay in the linked workspace. The version is checked as activation checks it (it can be read and its defaults fit its shape and the data limit), the workspace, its data and its first history entry are written in one transaction, and a refusal or a crash leaves nothing behind. The new workspace is saved as it is made and can be saved to the library as its own entry.
- **What is in the trash is out of reach.** Trashed workspaces and saved tools are not returned or listed, and changing one is refused with "restore it first" ([trash](trash.md)).
- **Times come from the store's clock**, which tests replace, so the trash's 30 days can be tested without waiting (`DATA-09`).

# Pitfalls

- **Two ways to change data.** `patchWorkspaceData` is for a tool's or chat's changes, checked per record; chat installs its optional final-data validator inside that transaction. Bridge callers do not install it yet. `saveWorkspaceData` replaces the data whole, checked against the workspace's revision; callers such as activation/restore own their shape validation. Neither low-level function automatically loads a tool schema.
- **Removed records' rows stay.** They are small and go with their workspace; a workspace whose tool adds and removes many records over years keeps one row for each. Pruning them would let a revision be reused.
- **Recovery snapshots don't travel in archives,** and nothing removes them while their workspace lasts; a retention limit, and assets kept by snapshots (`DATA-11`), come with the asset store (#49).
- **Restore's and undo's types are the contracts'.** The plan, its losses, the result, the recovery snapshot, the undo entry and their refusals are defined in the [contracts](../contracts/package.md) (`CON-01`), since the host app reads them through the [host API](host-api.md); a refusal this module can give must be listed there, or it doesn't compile.
- **Undo history doesn't travel in archives** either: an imported workspace starts with none, as with its revisions and snapshots.
- **Revisions don't travel in archives.** An exported workspace keeps its data and its revision; after an import every record starts at revision 1, so a change planned before the export can't be applied after it only by luck of matching counts. Plans don't outlive an import.
- **Two writers are module-internal.** `appendVersion` and `replaceData` write inside the caller's transaction; `addWorkspaceVersion`, `saveWorkspaceData` and `activateVersion` wrap them in one. They aren't exported from the module's index, and nothing outside it should call them. The same holds for `existingSavedTool` and `usableVersion`, the checks activation and Use again share.
- **`afterWrites` is for tests.** `activateVersion` and `useAgain` call it inside the transaction after its writes; a test throws there to stand for a crash. Production code never passes it.
- **Deleting is the trash's job.** Nothing here deletes a workspace or saved tool; the [trash](trash.md) (`DATA-09`) does, so nothing is removed without passing through it.
- **Errors for a missing ID are plain sentences**, but a title or name that breaks its contract (empty, or over 200 characters) throws zod's error; the API layer turns it into a plain message (#53).
