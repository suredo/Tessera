# Purpose

The host app that runs in the browser. Vite builds it, and React 19 renders it with the React Compiler on (A15). The local server serves its build, with the [host API](../server/host-api.md) it talks to. Its main screen has the workspaces beside the open workspace's tool (`APP-01`, `APP-03`), and a first-run screen while there are none (`APP-02`). My tools, the saved-tools library, is the second section (`APP-04`), and the open workspace's history, with its versions and undo, sits under its tool (`APP-05`). The trash is the third section (`APP-08`). Each workspace and saved tool exports to a file, and a file imports from beside the workspaces or from the first-run screen (`APP-06`). The chat that makes tools comes with M2. Its text, like all host text, goes through the translation layer from the first component (`UX-05`), so adding a language needs a message file and no code changes. Only English ships at first (A10).

# Entry points

- `src/DataChangeOffer.tsx` shows complete before/after facts for entry changes in a named workspace, preserving nested values and distinguishing empty text/list/object/null. Only host stable IDs are hidden. Apply/Cancel submits the opaque one-use token; neither choice resends a patch. `generate.ts` distinguishes committed data facts from review/unchanged/cancelled/refused outcomes. `App` refreshes lists/history and remounts the same tool after a successful data transaction so its initial data read sees the new entries.
- `src/App.tsx`: `App`, the main screen: it loads the workspaces and the library through the host API, keeps which workspace is open for the tab, and shows `EmptyState`, the first-run screen, while there are none, with the trash notice when the last one was just deleted, a way to the trash while it holds something, and importing from a file. The workspaces come most recently used first when the app opens, and keep their places after that.
- `src/Workspaces.tsx`: the workspaces list, each with its name, when it was last used and whether it is saved, with opening, renaming, saving to my tools under a name, and moving to the trash (`APP-03`).
- `src/Library.tsx`: my tools, the saved-tools library (`APP-04`): each saved tool with its name, when it was last updated (the entry or the workspace it follows, whichever changed later, A32) and the workspace Continue opens, searchable by name, with Continue, Use again (`DATA-07`), Save as a new tool, renaming and moving to the trash.
- `src/History.tsx`: the open workspace's history (`APP-05`): its tool versions, newest first, with restore; undo of its last data change (`DATA-04`); and the copies kept before a restore that lost data, which can be brought back (`DATA-10`). After a restore or an undo, the app starts the tool again with the changed data.
- `src/Trash.tsx`: the trash (`APP-08`, `DATA-09`): each deleted workspace and saved tool, with the saved tools that went with a workspace, when it was deleted and when it goes for good, and restore. Emptying it early first lists everything that goes.
- `src/Status.tsx`: the status screen (`APP-07`): Claude Code's status, Node.js, the data folder and its size, each failure with its fix (`PLAT-03`), Check again, and the probe (`CLI-02`). `SetupNotice` says on the first-run and main screens that Tessera can't make tools yet, and why, with the way to the status screen.
- `src/RequestBox.tsx`: where the person says what they need (`GEN-01`): a field and its button, the start of the chat (#132). Enter sends; Shift+Enter starts a new line.
- `src/generate.ts`: `askToGenerate` sends a request to the server's generate route and checks the reply against its contract; `carryOut` carries out a request: it stages a candidate behind the smoke check (`RUN-03`, `VER-02`), and the server activates it (`DATA-10`). It says what happened in plain words, as a `RequestOutcome` (`RequestDeps` lets a test give its own server and staging).
- `src/setup.ts`: the app's side of the [setup routes](../server/setup.md): `checkSetup` and `runProbe`, checked against the contracts, and `formatBytes` for the data folder's size.
- `src/archives.ts`: the app's side of the archive routes ([export and import](../server/archives.md)): `exportArchive` asks for a workspace's or saved tool's file and gives its name and bytes, `saveFile` has the browser save it as a download, and `importArchive` sends a file and gives back the report of what came in, checked against the contracts.
- `src/ImportFile.tsx`: `ImportFile`, the control that picks a `.tessera` file to import.
- `src/NameForm.tsx`: the small form that names something, for renaming, saving and Save as a new tool.
- `src/ToolPanel.tsx`: the open workspace's tool, run through the [runtime](../runtime/package.md) with the bridge to its saved data, with minimize, show again and full screen (`APP-01`).
- `src/tool-start.ts`: `startTool` opens the workspace through the host API, then starts its tool and serves it the bridge, and says after each change the tool saved (`StartOptions`); `rememberedState` and `rememberState` keep, for the tab, how each workspace's tool was left.
- `src/host-api.ts`: `ask`, the app's side of the host API: it sends an action and checks the answer against the contracts (`CON-01`); a refusal is a `HostError` with the server's plain words, and an answer it can't read is one with the host's own, from the translation layer.
- `src/app.css`: the host's look, from the UI standard's tokens, which `main.tsx` sets as `--ui-*` variables from the same tokens the tools use (the runtime's UI standard).
- `src/main.tsx`: starts the app in `index.html`, sets the page title and the UI tokens, and loads the styles.
- `src/i18n/translate.ts`: `t`, the host's translator, and `createTranslator`, which builds one for a language.
- `src/i18n/en.ts`: `en`, the English host text by key. `MessageKey` is its list of keys.
- `vite.config.ts`: the build, with the React Compiler as a Babel preset. Run it as `pnpm build`.
- `e2e/shell.spec.ts` and `e2e/app.spec.ts`: the app's browser tests, run as `pnpm e2e` with the repository's `playwright.config.ts`, against a real Tessera that `e2e/support/app-host.ts` starts through the launcher on a temporary data folder, serving the built app (which Playwright's web server builds first). They open the app in the installed Chrome and Edge at 320 px and 1280 px wide and records a video into `test-output/playwright/` (`TEST-06`). `e2e/prune-runs.ts` keeps the last 3 runs there. A failed test also keeps a light trace there, with its actions and console, and the runtime's test host page logs any task that blocks it for a second or more, so a stalled page can be told from a slow browser (#83, #98). The trace has no snapshots, and so no network: Playwright takes snapshots inside every frame, which counts as the person's activation there and would let a tool write before any click (`GEN-06`). The [CI workflow](../ci/workflow.md) runs it in its Windows job on every pull request.

# Invariants

- **Cancel belongs to one request, across navigation and entry review** (`CLI-06`, `GEN-08`). `src/request-control.ts` registers a host capability before generation. Cancelling during registration stops locally and revokes the returned capability before generation can start. The app retains that owner through smoke repair, mixed entries and review confirmation; a late callback cannot cancel a newer owner. A global, translated keyboard button remains available on other screens. It follows the outcome notice, which stays the first status, so its own empty status never hides that notice. It aborts staging locally and revokes pending server authority, without aborting generation, activation or entry-commit HTTP calls. Confirmed activation/data replies remain applied, even after Cancel; mixed outcomes keep the confirmed interface fact. A cancelled candidate cannot start staging or another repair/data continuation. Cancel/control HTTP waits and cancelled response waits are bounded to ten seconds; a missing reply reports uncertainty and refreshes data/history, never rollback. This is the Cancel slice of [#152](https://github.com/suredo/Tessera/issues/152); actual server stage names and elapsed time from [ADR 0010](../../decisions/adr/0010-generation-progress.md) still need the progress transport.

- **Staging retains the original request deadline** (`GEN-11`). `carryOut` gives staging the candidate's one-use activation token and a signal aborted at its server-owned expiry. Smoke repair and mixed data follow-ups also carry that token, binding their continuations to this request even when code hashes repeat. Expiry ends the wait without another smoke repair. The server checks authority again at activation. A confirmed activation remains successful even if its response arrives after expiry; a lost activation response says the outcome is unknown and reloads workspace data/history (`GEN-08`). The [deadline browser scenario](../../../packages/web/e2e/request-deadline.spec.ts) holds the wrapper before mounting, advances the browser clock and checks that staging is removed without activation or repair. Unit tests cover deadline signals, late successful activation and lost responses.

- **Library frame assertions wait for the named tool to run** ([#194](https://github.com/suredo/Tessera/issues/194)). Continue and Use again first verify the selected workspace, scroll its named tool panel into view and wait for its running-only Minimize control before reading nested-frame text. A selected sidebar card alone does not establish runtime readiness. Exact text/data checks and existing timeouts remain; no retry hides the earlier unresolved-frame failure.
- **Editing keeps the current tool until a candidate activates** (`GEN-07`, `GEN-08`). `carryOut` stages create and edit candidates alike, but says updated only for an activated edit. Unchanged and stale answers never stage. A repeated smoke failure keeps the old version and entries; a successful edit refreshes the workspace so `ToolPanel` restarts on its changed version. Browser edit tests cover dark styling, a no-op, a quantity migration preserving ids/values, repeated smoke failure and successful smoke repair without creating another workspace.
- **Mixed outcomes keep both facts** (`GEN-04`, `GEN-08`). After activation, `carryOut` refreshes the displayed interface before asking for the pending data plan. `askToFinishData` accepts only data replies. `withInterfaceOutcome` preserves the verified interface result through data review, cancellation, refusal and failure. A lost response says the entry result is unknown and reloads entries/history; it cannot claim nothing applied. An unchanged interface still permits the separate data plan. The serial mixed browser scenario covers delayed data planning after visible activation, cancellation, provider failure and repeated interface smoke failure with no data call.
- **Review must distinguish the stored values.** Text is labelled and quoted, numbers are labelled, and null/booleans/empty structures have distinct descriptions. A literal string such as "None" cannot look like null. Text and field labels preserve whitespace, so newlines/spaces remain visible. Before/after facts include nested fields; only each record's host ID is hidden.
- **The chat-data browser scenario is serial** ([#186](https://github.com/suredo/Tessera/issues/186)). Its steps share a workspace and reply sequence; later steps must be skipped after a failure rather than run against a restarted empty worker. Assertions after confirmation/undo wait for the host's completion notice and the replacement runtime's running control before reading nested frames. No retry or timeout increase hides a frame-replacement race.

- **Lint-rule snippets use a small typed project** (`ENG-20`, [issue 177](https://github.com/suredo/Tessera/issues/177)). `test/lint.test.ts` uses the repository's unchanged ESLint configuration on `test/fixtures/lint/App.tsx`, whose own tsconfig includes only the fixture and its imports. It no longer loads the real app and all browser tests for a few snippets. The original timeout and assertions remain, with an added unsafe-assignment case proving type-aware rules still run.

- **A smoke failure gets one repair before the final outcome** (`GEN-09`). `carryOut` sends a failed candidate's workspace, hash and complete smoke reason through `askToRepairSmoke`, then stages the repair behind the same smoke check. A startup failure can use this repair too; cancellation and activation refusal cannot. A second smoke failure ends the request. The reply's name and summary are used only after its activation; a repair failure or cannot answer is worded as that outcome. Scripted browser tests cover a repaired unlabelled field with the starting entries preserved, and a second failure that never activates.

- **No host text in components** (`UX-05`). A component asks `t("key")` for every word it shows, including `aria-label`, `title`, `alt`, `placeholder`, `label`, and the `value` of a submit, button or reset input. The lint rule `tessera/no-host-text` (`scripts/eslint/no-host-text.mjs`) fails on text written in a component, also when it is reached through a condition, a fallback, a concatenation, a template or a list. It never looks inside a function call, so `t("key")` passes.
- **Chrome and Edge are the supported browsers** (`RUN-06`): the browser tests run in both, and CI runs them. Firefox is best effort and isn't tested. Embedded browser panes that can't load nested sandboxed frames are unsupported; the Claude desktop app's built-in pane couldn't mount the POC's tools.
- **A missing key is visible, never silent.** The translator falls back to English for a key another language lacks; a key no language has shows as the key itself. Either way it reports the gap through its `onMissing` handler, which warns in the console by default.
- **Exactly one tool runs** (`RUN-02`): the tool panel makes a runtime for the open workspace and closes it when another opens, and its frames go with it.
- **The open workspace survives a reload** (`UX-07`): which one is open is kept in the tab's session storage, and the app opens it again, or the most recently used one if it is gone.
- **A minimized or stopped tool stays so** (`UX-07`): the tool panel keeps each workspace's runtime state in the tab's session storage, so after a reload, or switching away and back, it shows the tool as it was left instead of starting it. Both are kept per tab: a new tab opens the most recently used workspace and starts its tool. The data itself is always saved on the server, whichever way the tool was left.
- **A closed panel never starts its tool** (`RUN-02`). Starting waits for the server's answer before opening the tool; if the panel closed meanwhile, as React's development mode does once to every new panel, `startTool` stops at whichever step it is, so no tool runs in a runtime nobody can close.
- **"Last used" means opened or changed** (`APP-03`): the app tells the server each time a workspace opens, picked or opened by default, whether or not its tool starts, and shows the server's answer at once: whichever is later. The list is sorted by it when the app opens; after that, rows keep their places, so none moves under a click or takes the keyboard focus with it.
- **One start at a time** (`RUN-02`). "Show again" goes while its start runs, and the panel ignores a second one, so two starts never race for one runtime and leave a tool running without its bridge.
- **Continue opens exactly the linked workspace** (`DATA-07`), and says which before: its accessible name names the workspace. Use again opens a new workspace from the tool's starting data, and the entry still continues the first. Save as a new tool does the same under a new name and saves it as its own entry, so the variant changes apart from the original (`DATA-08`).
- **A restore is planned, then confirmed** (`DATA-10`). Restore asks the server for its plan first and shows it: the data stays, or exactly these values would be lost, each in plain words from the server's steps (`lossText`): "Buy milk: done was false", "Trip › Milk: note was "oat"" for an item in an item's list, "An item in tasks: …" for one without a name, and "heading was …" for a field outside any list; never a record's ID (`GEN-12`). A copy is kept. Only the confirmation runs it, against the data revision the plan was made with, so data that changed meanwhile makes the server refuse it rather than lose something unseen. Cancel changes nothing.
- **The history shows the tool's changes at once** (`APP-05`). A change the running tool saves goes straight to the server; the tool panel hears each one that was saved, never one refused, and the history loads again, so it can be undone without leaving the tool.
- **Undo undoes the change the person sees** (`DATA-04`). A running tool may change the data after the history loaded; Undo checks that the change it shows is still the newest, and if not, shows the newer one and undoes nothing. An interface change is undone by restoring the version before it.
- **Emptying the trash removes only what the person was shown** (`DATA-09`). The confirmation lists every entry, and the server empties the trash only if it still holds exactly those; if something was deleted meanwhile, it refuses, nothing goes, and the trash shows what it holds now.
- **The trash is never out of reach.** After the last workspace is deleted, the first-run screen offers the trash while it holds something, so that workspace can come back.
- **An import says what came in, then opens it** (`APP-06`): the workspace by name, with its saved tools, and when something with the same IDs was already here, that it came in as a copy and nothing here changed. A refused file shows the server's plain reason, and nothing comes in.
- **The host is accessible** (`APP-11`). `e2e/a11y.spec.ts` runs axe (`@axe-core/playwright`) on every host screen, form and confirmation, on the sample workspaces (the [development data](../scripts/dev-data.md)): the first-run screen, the main screen with a running tool, full screen, a restore that keeps the data and one that would lose some, a workspace's rename and save forms, my tools and its two naming forms, and the trash with its emptying confirmation. It fails on any WCAG 2.2 A or AA violation, leaving out a tool's own frame, which has its own floor (`RUN-05`). It also checks directly what a checker can't judge: on each of those screens, the first-run screen included, nothing moves when reduced motion is asked for, and the app works by keyboard alone, reaching each control with Tab and Shift+Tab, into a form and a confirmation, with the focus showing a 3 px outline on each.
- **A request becomes a running tool only through staging.** The server makes a candidate and stores it with its workspace and starting data ([generation stages](../server/generation.md)); the app stages it behind the smoke check, and only an activated one is called ready and opens. A candidate that fails its check, or is refused, is never called ready. The server tries schema and static repairs before answering; smoke repair follows browser staging (`GEN-09`). The scripted browser tests cover a static failure after repair, a successful smoke repair and a repeated smoke failure.
- **Every outcome is said in plain words** (`GEN-08`, in part): clarify, unsupported, "cannot" with the model's reason, ask to split, "not yet" for changes to a tool, and a failure with its plain message. The full outcome messages, with verified facts, come with #150.
- **The request box is offered only once the setup check passes** (`PLAT-03`), on the first-run screen and above the open tool. The app, not the box, knows a request is running, so leaving the screen and coming back never lets a second one in while the first runs.
- **A saved tool a request matches is offered, never opened** (`GEN-18`): the notice names it, with Continue (its linked workspace, as it was left) and Use again (a new workspace from its starting data), and nothing opens until the person chooses.
- **The setup check runs when the app opens** (`PLAT-03`). While it fails, the first-run and main screens say what is wrong, with the fix on the status screen, and the probe isn't offered. The chat (#132) will not be offered either; the app keeps the report for it. Check again shows a fix at once. A check that couldn't be made (the server didn't answer it) says so on those screens, never "Checking" without end, and Check again tries once more.
- **The probe runs only when asked** (`CLI-02`). Its button says it costs one call, and the result says in plain words how it went.
- **No browser test reaches the real Claude Code** (`ENG-11`). The test host's setup check finds a ready, fake one unless a test passes its own state; `e2e/status.spec.ts` runs the real check against a faked CLI for each state, and the probe against the fake claude program.
- **Buttons say which workspace they act on.** Their visible labels are short ("Rename", "Move to trash"); their accessible names include the workspace's name.
- **The React Compiler does the memoizing** (A15). No hand-written `useMemo`, `useCallback` or `React.memo` unless profiling shows the compiler missed a case, with a comment saying so. ESLint runs the hooks rules and the compiler's rules (`eslint-plugin-react-hooks`, `recommended-latest`) on every component.

# Pitfalls

- **Versions have no change summary or check results yet.** `APP-05` asks for both, but a version records neither until generation and the checks exist ([issue 121](https://github.com/suredo/Tessera/issues/121)).
- **A saved tool has no description yet.** `APP-04` asks for a short one, but nothing stores one until generation can write it ([issue 119](https://github.com/suredo/Tessera/issues/119)); search matches names only.
- **Keys are typed.** `t` accepts only keys that exist in `en.ts`, so a new string starts there. Another language's file may leave keys out; they fall back to English.
- **The title in `index.html` is empty on purpose.** `src/main.tsx` sets it from the translation layer.
- **The package's TypeScript settings include Node's types,** for its tests and build config. `src/` must still use only browser APIs.
