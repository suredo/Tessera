# Data and persistence (`DATA`)

| ID | Requirement |
| --- | --- |
| DATA-01 | **Storage: SQLite on the local server** (decided, A9). Workspaces, versions, data, saved tools, the trash and the call ledger live in a SQLite file managed by the local server, in the data folder (`PLAT-04`). Binary assets live beside it as files (`DATA-11`). Data survives browser changes and can be backed up. The browser holds no source of truth. (The POC kept everything in one browser profile's IndexedDB, and demos were lost to anyone without that profile.) |
| DATA-02 | **Changes are validated patches.** Data changes from chat are patch operations on stable IDs (add, replace, remove). They are resolved one at a time against a working copy and applied atomically. Revisions are tracked per record: a patch is rejected only if a record it touches changed after the patch was planned, so the person can keep using the tool while a chat change is prepared. Adds to a collection never conflict with other adds. On a conflict, the person's own change in the tool wins, and the reply says plainly what was not applied. AI changes never replace a whole object. (The POC had both a whole-object data loss and a "rename the wrong record after a delete" bug.) |
| DATA-03 | **Per-tool data schema.** Each tool declares a versioned data shape and reusable defaults. Shape changes include a bounded, deterministic migration, validated against source and target schemas on a copy. Prefer declarative transformations; generated migration code follows `SEC-01` and never runs in the server process. Compatibility and activation follow `DATA-10`. |
| DATA-04 | **Immutable versions and undo.** Tool versions are immutable and hashed, including their schema/defaults and dependency pins. Interface undo/restore creates a new version and retains current data under `DATA-10`. Data undo reverses only the eligible change, with a revision check that rejects intervening edits rather than overwriting newer work. Data undo history is kept per workspace up to a stated limit (proposed: the last 100 data changes); older entries are discarded, and the whole history goes when the workspace is removed for good. Undo entries keep the assets they refer to (`DATA-11`). Historical data recovery is explicit, never an automatic consequence of restoring interface code. |
| DATA-05 | **Export and import.** A workspace or saved tool (versions, data and the assets they reference) exports to a single archive file and imports back, with validation, including asset hashes. This is also how test fixtures are made (`TEST-04`). |
| DATA-06 | **Size limits stated.** Data size limits are explicit and reported plainly when hit. Proposed starting limit: 256 KiB of structured data per tool (the POC's 32 KiB was enough for its planners), revisited with real use. Assets have their own limits (`DATA-11`). |
| DATA-07 | **Continue or use again** (A21, A44). **Continue** reopens the saved entry's explicitly linked workspace and current data. **Use again** creates a separate workspace from that entry's current tool version and reusable defaults only, excluding session entries, original-request data and examples. It does not retarget the saved entry's Continue link. The new workspace is autosaved and can be added as its own named library entry. Show the linked workspace when offering Continue so the target is unambiguous. |
| DATA-08 | **Always saved; the library is named** (A30). Every workspace, version and data change is written to storage as it happens; there is no "unsaved work". **Save to my tools** adds a named entry to the library, which is what Continue, Use again and finding saved tools work from. A saved tool follows its workspace's latest version (A32), so later improvements are kept. Older versions stay restorable (`APP-05`), and **Save as a new tool** makes a separate entry when the person wants a variant. |
| DATA-09 | **Trash** (A31). Deleting a workspace or saved tool moves it to the trash, where it can be restored for 30 days. After that it is removed for good. Emptying the trash early needs confirmation that names what will be removed. Nothing is deleted without passing through the trash. An asset is removed only when nothing references it any more, including undo history, trash entries and recovery snapshots (`DATA-11`). |
| DATA-10 | **Atomic activation, restore and recovery** (A45). Treat interface code, schema, reusable defaults, dependency pins and data revision as a compatible unit. Stage checks/migrations on a copy while keeping the committed unit recoverable; commit the new unit in one transaction only if the source revision still matches. A crash, failed check or stale revision retains the old unit. Restoring old code first tries to preserve current data exactly. If a valid conversion would omit information, show a concrete loss preview and warning, preserve the full current unit in a recovery snapshot, and require confirmation. If compatibility cannot be established, refuse activation and explain why; a generic warning is insufficient. Test schema-changing edits, lossy/cancelled restore, intervening writes and crashes during commit. |
| DATA-11 | **Binary assets** (A48). Photos, exported images and other binary files live in a content-addressed file store in the data folder (`assets/ab/abcdef….png`, named by SHA-256), not in SQLite and not inside tool data. SQLite keeps one row per asset (hash, type, size, dimensions, original name, created) plus the references to it; tool data refers to an asset by ID. Assets are immutable: an edited image is a new asset, so versions, undo and restore need no copies, and an image used by many versions is stored once. A new asset is written to a temporary file and renamed into place before its row is committed; a startup sweep removes files with no row. An asset is deleted only when nothing references it: no workspace, version, data undo entry, trash entry or recovery snapshot. An undo entry holds its assets until the entry is discarded (`DATA-04`), so replacing a photo with a cropped copy never makes the original unrecoverable while that change can still be undone. Types are checked by content, not file name: PNG, JPEG and WebP first; SVG is not accepted. Proposed starting limits: 25 MB per asset and 500 MB per workspace, revisited with real use. A tool receives an asset as a blob over the bridge and shows it through a local `blob:` URL; it never sees a file path. Metadata such as a photo's location is stripped from anything sent to a model. |
