# Verification (`VER`)

| ID | Requirement |
| --- | --- |
| VER-01 | **Static checks with a real parser.** Generated JavaScript is parsed (acorn or the TypeScript compiler). Checks cover forbidden APIs, undeclared bridge actions and capabilities, calls to methods that don't exist in the manifest, and direct reads of the system clock. Data writes at startup are the bridge's to refuse when they happen, not this check's (`GEN-06`, A60). The POC's token scanner could not follow aliases or scopes. |
| VER-02 | **Smoke check for every candidate.** In the verification panel the tool must: mount; render something; throw no errors for a few seconds; pass the accessibility floor (labelled inputs, named buttons); and show no horizontal page scroll at 320 px wide, the narrow width set by the UI standard (WCAG reflow). |
| VER-03 | **Verification profiles (internal, not tools).** The host keeps a registry of verification profiles: behavior patterns it knows how to test, for example "something with a list of items", "something that schedules with rules" or, later, "a simulation with a run control". **They are not tools and never appear to the person.** When a person's request for a new tool matches a profile, its prompt part asks the generated tool to expose stable hooks (element IDs, a data shape), and its synthetic fixture and behavior check run before activation. An edit keeps the profile its tool was checked by, or none, so a profile is never added or swapped by an edit (L-94). Every profile is one definition (`P3`). Hidden test hooks in matching tools are accepted (A19). Which profiles to build first follows from the real-life test scenarios ([the milestone scenario sets](../testing/milestone-sets.md)). Tools that match no profile get only the smoke check (`VER-02`) and are labelled "behavior not verified", unless acceptance checks derived from the request, the default for them after M3's experiment (A57), pass (`VER-09`). |
| VER-04 | **No hidden requirements.** Every observable requirement a behavior check enforces is generated into the prompt from the same definition (`P3`). (The POC's study check enforced an 18:00 rule and a visible helper that the prompt never mentioned, and live runs failed on both.) |
| VER-05 | **Checks only when relevant.** A person's policy, such as "never on Fridays", is their data, kept in the tool's entries with its history, never a check: a behavior check tests that rules work, with a rule of its own on a throwaway copy, and holds the tool to none of the person's, so an explicit change ("Fridays are allowed now") is an entry change that no check or evidence depends on (A64). Evidence belongs to the version it checked (`VER-08`). A check is chosen by the intent, and matching element IDs alone never impose one (L-28). Tested with no restriction, and with one introduced, changed and removed. |
| VER-06 | **UI standard.** The UI standard doc is the source. It is injected into prompts, backed by host stylesheets, and has a custom mode for explicit requests. It is the look for whatever the person didn't specify: what they ask for wins, without their having to say they don't want the standard. So the static style check notes where a tool's look differs, for the next edit and the details view, and never refuses a tool (A63). This is ported from the POC (a historical copy is kept in [poc/ui-standard.md](../poc/ui-standard.md)). |
| VER-07 | **Useful diagnostics.** Every check failure says what was expected, what was observed, whose rule it is (the person's, a verification-profile rule, or a reference value), and gives hints for common mistakes (unit factors of 60, 1000 or 3600). |
| VER-08 | **Verified status is visible.** Each tool version shows whether its behavior was verified and by which checks, in plain words for the person and in detail in the details view. |
| VER-09 | **Acceptance checks from the request** (experiment in M3, A49). A separate stage, not the generator, turns the request into a few structured acceptance checks: starting data, an action through a named hook, and the expected observation ("after adding cheese, the list shows 5 items"). The checks go into the generation prompt as requirements (`VER-04`), the generated tool exposes the hooks they name, and the host runs them in the verification panel before activation. The generator never writes the checks it is judged by. A passing tool is labelled "checked against your request", which is weaker than a profile's behavior check. A check that expects a text the tool already shows before its steps proves nothing: it fails nothing and isn't counted, so a tool is "checked against your request" only when at least one check proved something (L-93). M3 measured, against your verdicts, how often these checks are meaningful, fail a good tool or pass a broken one ([results](../../evals/reports/2026-11-10-acceptance-run.md)): they are the default for new tools that match no profile (A57), and M4's release run measures them again. |
