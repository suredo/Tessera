# Provider adapters: Claude Code and Codex CLIs (`CLI`)

For now Tessera reaches models through the signed-in Claude Code and Codex CLIs on your machine (A3): they are quick to connect for local development and testing. These requirements turn every CLI problem from the POC into a design rule. API keys and other providers come later through the same interface (`CLI-10`).

| ID | Requirement |
| --- | --- |
| CLI-01 | **Adapter interface.** `run(stageSpec) → { value, usage, raw }`, where `stageSpec` includes prompt, schema, model, effort, tool policy, time limit and cancellation signal. Claude Code is the first adapter (M2); the Codex CLI follows in M3 behind the same interface and contract tests (A5). The interface assumes nothing CLI-specific: structured output is requested from a JSON Schema and validated by the host whatever the provider promises, usage is normalized (`CLI-04`), and model and effort names are mapped per provider, so API-key providers fit later (`CLI-10`). |
| CLI-02 | **Executable resolution and probe.** Use an absolute path to the real executable (`claude.exe` on Windows; the npm `claude.cmd` shim cannot be spawned). The same applies to the Codex CLI. At startup, probe and show: version, sign-in status, and a tiny structured-output call (opt-in, because it costs a call). Sign-in comes from `claude auth status`, which reaches no model, and is checked before any call is spent: a CLI that isn't signed in still fails a call (L-71, [ADR 0002](../decisions/adr/0002-claude-code-cli-contract.md)). |
| CLI-03 | **Locked flags per stage.** Normal stages have safe mode, tools disabled, no MCP servers/session persistence, `dontAsk` permissions and a small turn limit. Only research gets web tools. No stage gets file tools; the evaluation reviewer receives approved screenshots as image inputs (`CLI-08`). Document every flag per adapter, enforce a tested CLI version and cover exact arguments with fake-process tests. Tested for Claude Code 2.1.296 ([ADR 0002](../decisions/adr/0002-claude-code-cli-contract.md)): `--print --output-format json --json-schema --model --effort --tools "" --safe-mode --strict-mcp-config --no-session-persistence --permission-mode dontAsk --max-turns --system-prompt`, then the request. `--max-turns` is not a hard bound (L-73), so every call is also bounded by its time limit and its turns are recorded. The CLI passes the schema to the API as a tool's input schema, which must be an object at the top level, so each contract travels wrapped as `{ answer: <contract> }` and is unwrapped before it is checked (L-72). |
| CLI-04 | **Normalized usage.** Input totals include uncached input, cache writes and cache reads; cached input is shown separately. Failed and cancelled calls are recorded, with unknown values marked unknown, never as zero. |
| CLI-05 | **Error mapping.** Sign-in, usage limit, unavailable model, unsupported effort, schema failure and turn limit each map to a plain message. Provider errors stop the request; they are not repaired. A failure is read from the result's `is_error` and its error fields, never from `subtype`, which can say `success` for a failed call (L-71). |
| CLI-06 | **Job control.** One AI job runs at a time; this is configurable. A cancellation while queued means the job never starts. A newer request may replace a running one: the running job is cancelled and recorded as cancelled, its chat message stays visible and marked as not done, and the new request runs. No request disappears without a trace. (In the POC, a newer request replacing a running one lost both.) |
| CLI-07 | **Progress.** If the CLI's streaming output mode can report progress without breaking structured output, use it for `GEN-16`. Otherwise show elapsed time and stage names. Decided in [D7](../decisions/open/d07-progress-streaming.md). |
| CLI-08 | **Clean environment and no file tools.** Use a temporary working directory. Start the CLI from an allowlisted environment: only what it needs to start and find its sign-in. That keeps out `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and the matching Codex variables (such as `OPENAI_API_KEY`) unless API billing is explicitly allowed, and the variables a parent Claude Code session sets, such as `ANTHROPIC_BASE_URL` and `CLAUDE_CODE_SIMPLE`, which change where and how the CLI calls the model (L-74, [ADR 0002](../decisions/adr/0002-claude-code-cli-contract.md)). No stage exposes file tools to the model. A temporary directory is not an OS filesystem sandbox, and the trusted CLI still needs its sign-in/configuration files. The evaluation reviewer gets approved, sanitized screenshots as image inputs (A27). If an adapter cannot pass images, the reviewer works from source, host facts and page text, and the report says the screenshots were not reviewed. |
| CLI-09 | **Default model routing** (starting point, A18): Haiku 5.5 low for intent and data actions; Sonnet 5.5 medium for creation and repairs; Sonnet 5.5 low for edits; Sonnet 5.5 medium for research (M5). Opus only by explicit configuration, never as an automatic fallback. The acceptance stage (`VER-09`) starts on Haiku 5.5 low. Codex routes are set when its adapter lands (M3). Each stage's route is configurable and recorded in the ledger. |
| CLI-10 | **Later: API keys and other providers** (A47). Signed-in CLIs are for your own local use. Before anyone else runs Tessera on their own machine (M6 trials, the installer), connections move to API keys or the person's own provider account, through adapters behind the same interface: Anthropic and OpenAI first, then other providers such as z.ai, Kimi and Grok. Anthropic's Agent SDK documentation does not allow third-party products to offer claude.ai sign-in or subscription limits without prior approval,[^agent-sdk] so subscription sign-in is never offered to other people. Each new provider gets contract tests, a probe and a model-matrix run (`EVAL-05`) before it is offered. |

[^agent-sdk]: Claude Agent SDK overview
