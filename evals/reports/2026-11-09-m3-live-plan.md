# M3 live run: plan, 2026-11-09

This is the plan the live evaluation protocol asks for before any call (`ENG-07`, [live evaluation](../../docs/practices/live-evaluation.md)). It covers M3's scenario set ([milestone sets](../../docs/testing/milestone-sets.md)): T1, T2 in Portuguese, T3, T5 without export, T10, and one tool no profile fits. **Nothing runs until the owner approves the hard cap below.** Every scenario has a hand-written rehearsal that passes with no call, so the script has been rehearsed (step 2 of the protocol).

# What it is for

M3's goal is that the host knows whether a tool works ([M3 roadmap](../../docs/roadmap/m3-verification-and-codex.md)). This run answers, with real models, the exit criteria that need one:

- **The live run's checks pass, or fail with useful diagnostics.** Each tool that fits a profile meets its behavior check before it opens (`VER-03`), and a failure goes to one behavior repair (`GEN-09`).
- **Profiles matched wrongly are counted, with fewer than 1 in 10 wrong.** Seven requests make a tool, and each has a known right answer.
- **Do steps drive the real tools** through their profiles' hooks (`EVAL-01`), so a tool that passed its check is also used the way the person would use it.

It does not cover:
- **The AI technical review** (`EVAL-03`, `EVAL-04`): not built yet. The owner judges the screenshots and video, as in M2.
- **The acceptance-check experiment** (`VER-09`): its acceptance stage isn't built either. T6 runs here as the unmatched tool, so its smoke-only path is measured now.
- **The two-pass comparison:** it has its own plan.

Each of these gets its own plan, inside the envelope's remainder.

# Measures, frozen before the run

- **First-attempt pass rate:** the requests that pass their host facts at the first attempt, out of all requests in the six scenarios (A40). Lifecycle and do steps must all pass and are reported apart. A step that can't run because an earlier one failed stays in the denominator.
- **Behavior checks:**
  - For each version of a tool that fits a profile: whether its check passed at once, after its one repair, or not at all.
  - For each failure: whether its diagnostic says what was expected, what was observed and whose rule it is (`VER-07`), judged from the ledger.
- **Profile matching:** for each of the seven requests that make a tool (T1, T2, T3, T5, T10 twice, T6), whether the intent named the right profile (or none for T6). This is read from the recorded answers. The exit criterion is fewer than 1 in 10 wrong. **One wrong in seven fails it,** and that is reported as measured, not explained away.
- **Verified status:** each activated version's recorded checks and profile (`VER-08`), from the version notes.
- **Cost:** calls, input tokens (cached apart), output tokens and model seconds, from the harness ledger.
- **What it made:** the screenshots and video, judged by the owner as accept, accept with notes, or reject.

# Stop rules

As the protocol says:
- **Step 1 of a scenario fails:** that scenario stops; the next one still runs.
- **The same step fails twice:** stop that step, fix the cause offline, and ask before spending more.
- **A provider error** (sign-in, unavailable model): stop the run.
- **A usage limit:** pause, then resume the remaining scenarios after it resets.
- **The same failure in two scenarios:** stop, to fix the cause offline before spending more.

# Record

- **Each scenario's folder:** report, harness ledger, request log, screenshots per step and video, kept in `evals/reports/<date>-m3-live-run/`, as M2's are.
- **Recorded answers:** saved as replays in `evals/scenarios/replays/`, so the run can be replayed with no call (`EVAL-07`).
- **Defects:** every defect gets a lessons entry, a replay test and a fix (`ENG-13`).

**Asking for:** approval of the 46-call hard cap above, in M3's envelope of about 65.
