- **The hard cap is enforced by Tessera itself.** The sandbox starts Tessera with `TESSERA_CALL_CAP=10` (ENG-07): every model call counts, the probe's and both programs' included, and a call past the cap is refused before it reaches the program, which ends its request in plain words. It never grows during the run.
- **Why acceptance may run:** T1 matched the list profile in the M3 live run, so it had no acceptance stage; but the profile is the model's answer, and a request that fits none gets checks from the request first, as Tessera does by default since A57.
- **What one request may spend:** intent, acceptance and create, and one repair of each kind of failure (its data's shape, the static check, the smoke check and the behavior check, `GEN-09`), so at most 7. Claude Code's request goes first; if it uses more than 7 minus what Codex needs, the cap may refuse Codex's, which is then reported as stopped by the budget.
- **Two requests, never repeated.** A request that fails is recorded as failed, and no other request is asked. The status screen's probe isn't used.
- **M3's envelope** is about 65 calls, with 56 used ([budgets](../../docs/roadmap/budgets.md)). The cap of 10 could pass it by 1 at most; the expected 4 to 6 stay within it.

# Stop rules

- **The sandbox can't be prepared** (a download or the install fails): the run stops before any call, and the failure is fixed first.
- **The setup check can't be followed** for a program, so it never reaches ready: that program's request isn't asked, and the gap is the result.
- **A provider error** (sign-in, unavailable model, usage limit): that program's request ends, and it isn't asked again.
