# M2 speed, from the 2026-11-05 live run

This answers [issue 154](https://github.com/suredo/Tessera/issues/154): the speed targets (`OBS-04`) measured on the [M2 live run](2026-11-05-m2-live-run.md), and the time limits revisited (`GEN-11`). **No call was made:** the figures come from the run's own report and harness ledger, read by `node evals/src/runner/speed.ts` ([scenario runner](../../docs/code/evals/runner.md)) over the four live run folders (J6, T1, T6, T13).

## How it is timed

- **Model time per stage:** each call that ended well, from the ledger's duration.
- **Requests, as the person waited:** each request step's time in the run, from sending it until the host had said what happened, staging and the smoke check included. This run's report predates each step's recorded calls, so each request is matched in order to one intent call and the calls after it; that holds here, as the run has exactly one intent call per request (no intent retry). Later runs record each step's calls and are matched by them. What it did is the stage among them: create, edit, data, or only an answer. J6's request sent only to be cancelled isn't timed.
- **p50 and p95 are by nearest rank.** With fewer than 20 samples, p95 is the slowest one, so every p95 below is the slowest of a small sample.

## What it says

- **Every target the runner can measure is met,** by a wide margin: intent at 3.5 s against 10 s, the one data change at 11.4 s against 15 s, and the first useful tool at 31.6 s against 90 s, a repair included. **The samples are small:** 3 creations, 1 data change. A target met on three samples is a starting point, not a guarantee.
- **Not measured: host screens within 100 ms, and a saved tool opening and mounting within 5 s.** The runner times Use again and Continue only until the workspace switches (0.1 s to 0.2 s), not until the tool has mounted, and it doesn't time the host's own screens. They are left for M3's runs, said here rather than hidden.
- **The first-attempt pass rate** is in the live run report: 10 of 12 requests, 83%, against the 85% target.

## The time limits

The owner chose to **keep the time limits as they are** ([ADR 0012](../../docs/decisions/adr/0012-time-limits-after-m2.md)): 60 s each for intent and a data change, 180 s each for generation and repair, and 7 minutes per request. The slowest stages measured (create 14.8 s, edit 19.4 s) are far inside them. But three creations are too few to set a limit from, the POC's creations took 105 to 131 s, and two passes for big tools (`GEN-17`, [#153](https://github.com/suredo/Tessera/issues/153)) aren't built yet. They are revisited with M3's runs, against the same targets.
