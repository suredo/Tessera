## What M2 learned

- **The live run found what scripted tests couldn't.** Its four defects were all in what the person reads, not in what was stored: a stale message after Continue (L-77), a cancel worded as a failure (L-78), an unchanged edit that hid the model's reason (L-79), and screenshots taken too early (L-81). The host-fact checks passed throughout, because they don't read messages.
- **A strict check can stop a measurement.** The static check's startup-write rule refused real tools twice in the two-pass comparison, which stopped by its own rule after 10 of 30 calls (L-84). The owner kept the check strict, and the prompt now steers code the check can verify.
- **The CLI is a moving target.** Claude Code's schema validator, sign-in and inherited environment each cost a call or a fix before anything worked (L-70 to L-74). The adapter's contract tests and the version gate keep these from coming back.
- **Windows CI stalls, and its failures land on whichever test is running.** Several browser tests timed out on the runner after losing 13 to 27 seconds before the app was involved. The trackers move to M3.
- **A smaller tool must say it is smaller.** Asking for a video playlist made a plain list, called ready, with no word that tools here can't fetch or play videos (L-85). Answers now name what they leave out (#263).
- **The startup-write check gets in the way of everyday tools.** Both of the owner's first requests tripped it, and a calendar failed after its one repair (L-84), most likely on harmless code the analysis couldn't follow. As the owner chose, the check stays as strict; its finding now names the value it couldn't follow and how to fix it (#264), and the details view keeps the code of every answer, refused ones included (#265), so the next refusal can be read. If refusals keep blocking tools, the owner decides whether an unsure finding should go to the runtime guard instead.
